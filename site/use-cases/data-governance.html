Use Cases · Data Governance and Privacy

Governance is in the model. Provisa is the governed IR.

Lineage, masking, test environments and the audit log cover provenance, PII-safe analysis and PII audit. A regulator validates the provenance of a field in a regulatory report. A data scientist analyzes large datasets without exposing PII. A data management team publishes versioned datasets through self-serve requests. A data audit team audits PII usage.

The model's primitives: column-level lineage explorer and federation-wide lineage graph, column masking that blocks inference, data products flagged per table with time travel serving each version, and the query audit log as a governed table.

01 Scenario one — Lineage validation

A regulator or data officer validates, end to end, the provenance of a field in a regulatory report.

Column-level lineage explorer and federation-wide lineage graph. Every materialized-view refresh records each output column's upstream columns, transform, input snapshots and definition version; opt-in row-level delta capture adds the changed rows. Iceberg and Delta Lake time travel (as_of) re-runs a past report as it stood. Impact analysis shows what a column rename or drop would break.

A materialized view computes a regulatory report from upstream tables across multiple sources. When the view refreshes, Provisa records the lineage: for each output column, which upstream columns fed it, what transform was applied, which snapshots of the input tables were read, and which definition version of the view was used.

A regulator or data officer queries the lineage graph in the catalog to trace a field back to its source. Time travel re-runs a past report against the input snapshots that were live on that date. Impact analysis walks the graph forward to show what would break if an upstream column were renamed or dropped.

02 Scenario two — PII-safe analysis

A data scientist analyzes very large datasets without exposing PII, while the training data stays realistic and valid.

Column masking; masked columns are refused in WHERE and HAVING, which blocks inferring a value by binary-search filtering. Test environments either fake identifying columns on read (real rows, real distributions) or generate a fully synthetic model from profiles at any scale, so no real row exists. Consistent surrogate masking gives the same value the same surrogate every time, so joins, grouping and distinct counts stay valid.

A column tagged pii is masked for the researcher role. The masking transformation is defined once and applied in the governed IR, so every surface sees the same masked value. Masked columns are refused in WHERE and HAVING clauses, which blocks inferring a real value by filtering on it until only one row remains.

Test environments branch the model like git. One environment fakes identifying columns on read, so the rows are real but the PII is synthetic. Another environment generates a fully synthetic model from profiles of the real tables, at any scale, so no real row exists. Consistent surrogate masking gives the same real value the same surrogate every time, keeping joins, grouping and distinct counts valid.

03 Scenario three — Data products

A data management team acquires and publishes large, versioned end-of-day and end-of-month datasets to downstream consumers through self-serve requests.

Data products: a per-table flag that drives metadata export to catalogs. Time travel serves each version. Arrow Flight and the large-result redirect deliver bulk results. A consumer's GraphQL query is the provisioning request; when no product fits, the creation-request queue routes the ask to whoever may create it.

A table tagged as a data product exports its metadata to external catalogs. Time travel serves each version of the table: end-of-day snapshots on the day they were current, end-of-month snapshots on the month they were current. Arrow Flight delivers bulk results efficiently for large datasets.

A downstream consumer queries the product over GraphQL, and that query is the provisioning request. When no existing product fits, the creation-request queue routes the ask to a steward who may approve it, creating a new versioned product with its own terms and expiry.

04 Scenario four — PII audit

A data audit team audits PII usage.

The pii system tag classifies columns and is exported as a classification. An append-only query audit log records user, role, tables, status and duration for every query on every transport. It stores a query hash, not the query text.

Columns tagged pii are classified as such in the catalog, and that classification is exported to external governance tools. The query audit log is an append-only table in the ops domain, recording every governed query: user, role, tables touched, status (success or refused), duration, and a hash of the query text.

An audit team queries the log like any table to see who read PII columns in the last month, which queries were refused, and which roles accessed which tables. The log itself is governed: only the audit role may see it, and every query against the log is itself logged.
