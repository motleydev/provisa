Use Cases · AI Agents and Semantic Search

Agents query under governed rights. The same pipeline as any user.

Agents and vector search run under the same rights, row rules and sensitivity tiers as any other client. A procurement team builds a Claude agent that answers questions across ERP and logistics data. A support organization wants agents to find similar tickets without contractors searching enterprise accounts. A strategy analyst asks an agent one question and gets a number, a nested record and a network.

The MCP server (remote over HTTP with OAuth, or local) lets agents read the catalog and run SQL through the same governed pipeline. Multi-surface queries return SQL, GraphQL and Cypher from one natural-language question.

01Scenario one — MCP agents

A procurement team builds a Claude agent that answers "which suppliers are late on open purchase orders?" across ERP and logistics data, and flags data it cannot find.

The MCP server (remote over HTTP with OAuth, where the token maps to a role, or local) lets the agent read the catalog and run SQL through the same governed pipeline as every other client, so it sees only its role's tables and rows. When carrier data is missing, Provisa's chat assistant searches the org's GovData subjects, then Kaggle, then the web. It proposes sourcing the data, and the proposal enters the creation-request queue for a steward to execute or reject.

An agent works through MCP, calling Provisa's catalog and query endpoints. It sees only the tables and columns its role may see. When data is missing, the chat assistant searches public data catalogs and proposes new sources. Every proposal goes to the steward queue; the agent never registers anything itself.

02Scenario two — Vector search

A support organization wants agents to find resolved tickets similar to a new one, across the ticketing database and the product knowledge base, without contractors searching tickets from enterprise accounts.

An embedding column on tickets, generated from a subquery that joins subject, body and product name; the model comes from a registry (OpenAI-compatible, Ollama or a local HuggingFace model). Agents rank matches with cosine_similarity in SQL; a source without native vectors is materialized to pgvector transparently. Scheduled refresh re-embeds only changed tickets. Row-level security limits each agent to their accounts, and a restricted sensitivity tier blocks similarity search for the contractor role.

Tickets have an embedding column generated from subject, body and product. The embedding model is registered in the model registry. Agents query with cosine_similarity to rank similar tickets. Row filters keep each agent to their own accounts. A restricted sensitivity tier on the contractor role blocks similarity search on enterprise tickets.

03Scenario three — Multi-surface queries

A strategy analyst asks an agent one question and wants a number, a nested account record and a network, without knowing which query language suits each.

Through MCP, the agent sends the question once and gets back ready-to-run queries for all six surfaces (SQL, GraphQL, Cypher, gRPC, JSON:API, OpenAPI), each checked against the analyst's role. It runs SQL for the cost total, GraphQL for the nested account record, and Cypher for the account-supplier network. Every answer holds only what the analyst's role may see, so a masked or hidden property never appears.

The agent calls the natural-language query endpoint with one question. Provisa returns queries for all six surfaces, each checked against the analyst's role. The agent runs SQL for the number, GraphQL for the nested record, and Cypher for the network. The graph comes back as nodes and edges with a layout (force, hierarchy or ELK) for the client to draw.
