Provisa / Why / No lock-in
Vendor independence

A governance layer. Your data stays where it is.

Provisa is the governed join across the sources you already run. It holds the model, reads what the engine can reach in place, and lands a replica only where it cannot. It does not replace your databases, and it does not scan or patch anything itself.

01 Scope

Three things Provisa is not.

01

Holds the model, not the system of record

Provisa holds a model — sources, tables, columns, relationships, roles, rules — and a materialization store for the replicas the engine needs. Your databases and warehouses stay the system of record, and the Sources page says which paths copy and which read in place.
02

Not a replacement for your stack

You keep PostgreSQL, Snowflake, BigQuery, Databricks, MongoDB — whatever you run today. Provisa registers them as sources and reads them through the federation engine.
03

Not a warehouse, an ETL tool, or a catalog of record

It is the governance layer deciding which joins are legal and which columns a role may see. Your catalog can read its metadata; Provisa does not replace it.
02 Protocols

Every surface speaks a standard wire.

pgwire PostgreSQL wire protocol
Bolt Neo4j Bolt, Cypher
Flight Flight SQL, ADBC, JDBC
GraphQL GraphQL over HTTP

A client that speaks PostgreSQL connects to Provisa's pgwire listener without knowing what Provisa is. The same holds for Bolt, Flight SQL, ADBC and GraphQL clients. Where Provisa ships its own client libraries — a JDBC driver, a Python client — they ride Flight and DB-API, not a private protocol. The listeners and surfaces, in full.

AI AGENTS MCP (Model Context Protocol) is also supported, so an agent reaches Provisa the same way it reaches any other MCP server. An agent can propose a source but never create one, and every tool call is scoped to the identity's capabilities.
03 Engine slot

Change the engine without changing the model.

The engine slot holds the federation layer: Trino, PostgreSQL, DuckDB, ClickHouse, a cloud warehouse, or a generic SQLAlchemy target. What changes when you swap engines is which sources are reached in place and which land as a replica — not whether the model works. The same tables, relationships and rules; governance runs the same way on all of them.

The engines Provisa can run on
Engine Role Note
Trino Federator Default; widest connector reach.
PostgreSQL Federator Bring your own or embedded; federates through FDWs or pg_duckdb.
DuckDB Federator In-process; the desktop and demo default.
BigQuery Partial federator What it cannot reach natively lands in it first, with GCS external links.
AT BOOT The engine is chosen once per deployment and binds at start; changing it is a configuration change, not a remodel.

05 Export

The model exports as YAML.

The model — sources, domains, roles, tables and columns, relationships, metrics, row filters, commands, webhooks, scheduled triggers and naming rules — exports as one YAML file from the admin page or GET /admin/config/live. Applied to an empty store, it rebuilds the same model. GET /admin/ossie is a second, standards-based path.

curl → /admin/config/live
# The whole model as one YAML file
curl -H "Authorization: Bearer $TOKEN" \
  "$PROVISA_URL/admin/config/live" \
  -o provisa.live.yaml

# A subset — sources and tables only
curl -H "Authorization: Bearer $TOKEN" \
  "$PROVISA_URL/admin/config/live?sections=sources,tables" \
  -o subset.yaml
06 Import

Moving to Provisa is supported.

HASURA V2 → PROVISA Provisa reads a Hasura v2 metadata export directly: tracked tables, relationships, select, column and write permissions, remote schemas, computed fields, actions, event and cron triggers. The import is a starting point for review, not a finished migration. DDN (v3) projects import the same way. The full mapping, side by side.
