Governance

Governance is a rewrite of the statement, not a filter on the result.

Provisa does not run your query and then remove what you should not have seen. The caller's role rewrites the statement before it reaches your database — row predicates injected, masked columns replaced, invisible columns stripped, joins checked against what someone approved.

That rewrite happens at one place every surface goes through, so it covers GraphQL, Cypher, SQL over HTTP, pgwire, Bolt, Arrow Flight and gRPC without being written seven times. There is no query path that skips it.

01 The mechanism

One rewrite, before the database sees anything.

Compilation is two stages. The first turns the request — whatever protocol it arrived on — into plain SQL against the semantic model. The second rewrites that SQL under the caller's role, through subqueries, CTEs, joins and star expansion alike. Because the second stage needs only SQL and a role, every client path gets the same enforcement.

SELECT c.name, c.email, o.total
FROM customers c
JOIN orders o ON o.customer_id = c.id;
# Returns the governed SQL for a question, with row filters and masks
# inlined, plus the route, the parameters and the enforcement metadata.
# Executes nothing. The role comes from the session.
curl -X POST https://provisa.internal/data/compile \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"query": "{ customers { name email orders { total } } }"}'
# Takes SQL. Returns the engine's own annotated EXPLAIN of the governed
# statement, with the optimizations that fired. A different thing from tab 2.
curl -X POST https://provisa.internal/data/sql/explain \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"sql": "SELECT c.name, c.email, o.total FROM customers c JOIN orders o ON o.customer_id = c.id"}'

The question, whatever protocol it arrived on, compiles to a PostgreSQL-style statement against the semantic model with the caller's role applied. What comes back is the compiled statement and an enforcement object that names, per table and per column, exactly what was applied:

The fields of the enforcement object returned by POST /data/compile
Field What it holds
rls_filters_applied The predicate text injected, per table
columns_excluded table.column for every column stripped for this role
masking_applied table.column -> <mask_type> per masked column
schema_scope role:<role_id>
ceiling_applied The row or time ceiling, when one fired
route The routing decision
This is how you answer "what would this role actually be able to see" without running anything against production — and how your own reviewer answers it without taking our word for it. The enforcement is enumerable before the query runs, by field name, per role. That is an auditable artifact, not a screenshot.
02 The layers

Five layers compiled into the statement, in enforcement order. Then one decision taken before it runs.

00
Introspection filtering Schema and catalog generation, per role Objects outside a role are absent from the schema, the catalog and the browser. A hidden table is not one the reader discovers and is then denied — it is not in the catalog they were handed.
01
Domain access Compiler validation, before execution A query touching a table outside the role's domain access is rejected before anything runs.
02
Row-level security Governed-SQL rewrite Per-table, per-role WHERE injected into every SELECT, evaluated against the raw data rather than against a masked projection.
03
Column visibility and masking Governed-SQL rewrite Invisible columns are stripped and masked values replaced before results leave the server. Four mask types: regex, constant, date truncation and consistent-fake.
04
Predicate guard validate_sql, pre-execution A masked column is refused in WHERE and HAVING, at parse time.
Before execution — the approval hook An ABAC callout, outside the plan Your own decision service can refuse the statement before it runs. It is not one of the five, because it is not compiled into anything — it is a question we ask on your behalf. §7 has it in full.

Five is the number of layers compiled into the statement. The one thing on this list that is not in the product: public-column publishing — serving a published column to an unauthenticated reader — is designed and not built, so it is not a layer and is not counted. We would rather tell you than have you find out.

03 Why layer 4 exists

A masked column you can filter on is not masked.

Masking a column and then allowing it in a WHERE clause leaves the value recoverable: a caller runs the query repeatedly, narrowing the predicate, and binary-searches the value they were never shown. Provisa refuses a masked column in WHERE and HAVING at parse time, before execution.

-- role: analyst. `customers.email` is masked for this role.
SELECT count(*) FROM customers WHERE email LIKE 'a%';
-- refused at parse time: a masked column cannot constrain a result
Masks leave filters and joins working on the real value where the role is allowed to see it, and refuse the predicate where it is not. The raw value never leaves the database.
04 The join guard

Every join in SQL and Cypher must match a relationship someone approved.

A join — or a graph traversal, which is the same thing a layer down — is checked against the approved relationship catalog at compile time. A join that no approved relationship covers does not run.

It is policy, not a security boundary — and here is why that matters

The relationship guard is governance policy. It has two bypasses and we would rather you heard them from us: a role holding the ignore-relationships capability joins freely, and a role with the guard disabled and an explicit directive in the statement does too — either one alone does nothing. It is also skipped for GraphQL, where relationship fields are pre-approved by the schema itself and the check would be redundant.

In high-security mode, neither bypass applies

Turn on high-security mode and the guard is unbypassable, by anyone — including a role that was granted the bypass capability by mistake. That is the property worth having: not that misconfiguration is impossible, but that one setting makes it survivable.

Why open the explorers at all

Because every path a person or an agent can take is one someone approved. People roam the model freely and an agent discovers what connects to what, and the edges are the control.
05 Reach

Absent, not denied.

A query runs inside a domain

Plus whatever is reachable from it by approved traversal. Everything outside that graph is not refused — it is not there. For a reviewer writing a control narrative, "structurally unreachable" and "denied on request" are different controls, and only one of them survives a creative query.

Four schemas, generated per role

The GraphQL SDL, the SQL information schema, the Cypher label catalog and the gRPC proto are each generated for the role asking. Unauthorized objects are structurally absent from all four.
06 Your decision service

When your policy engine owns the decision.

For rules too situational to write as a predicate, Provisa calls out before the query runs — over a webhook, gRPC, or a Unix socket. It is scoped per table, per source, or deployment-wide, and a circuit breaker protects queries when the hook is unhealthy. This is where request-time context enters: a ticket number, a break-glass approval, a time window.
If the answer to "who decides" is "our own system", this is the integration point, and it sits before execution rather than beside it.
07 Audit

Append-only, and the database refuses the edit.

What is written

Every query: tenant, user, role, a hash of the query, the tables touched, the source, status and duration. Written at the single governed pipeline, so no surface can skip it.

What is never written

Query text in the clear. The hash identifies the shape; the text is not stored.

What the database refuses

UPDATE and DELETE against the log, by rule, at the database — not by application logic that an administrator could route around.
That immutability is enforced by PostgreSQL rules, so it holds on a PostgreSQL control plane — which is the default from the desktop install up, not only in production. SQLite is a selectable control-plane store and it does not enforce the rule; there, append-only is a convention of the application rather than a guarantee of the database. If your control narrative depends on database-enforced immutability, you already have it, and this is the sentence that tells you which setting would take it away.

The access record and the other internal logs are exposed as queryable tables in the built-in ops domain, so the audit trail is a governed table like any other rather than a log file to grep. Curated management reports over those tables are being built; the tables themselves are there today.

08 Keys

The master key is yours, in your own KMS.

What protects a payload, where the master key lives, and what revoking it does
How payloads are protected Envelope encryption, AES-256-GCM, with a unique data key per payload wrapped by the organization master key.
Where the master key lives A customer-managed key in your own AWS KMS, Azure Key Vault, Google Cloud KMS or HashiCorp Vault Transit. Provisa never stores raw key material, and a provider you run yourself registers without core changes.
What revocation does Revoke the grant and the data is unreadable. Not "access is denied" — unreadable.
Bulk results Results written to object storage can be encrypted with a key only the client holds; the JDBC driver, the Python client and GraphQL clients decrypt on their side, so the server never sees the clear text.
High-security mode The relationship guard becomes unbypassable and the wire-protocol listener can be turned off entirely.
09 What we do not claim

We hold no certifications. Here is what we do hold.

Provisa gives you the controls an auditor asks for: an append-only access record the database itself will not let you edit, envelope encryption under a key held in your own KMS, and an air-gapped deployment that never phones home. The certifications belong to the environment you run it in; the control evidence is per-requirement and exportable.

Provisa is self-hosted. You run it on your hardware, in your cloud account, or air-gapped. There is no managed service to buy today — we never touch your data, we run no service on your behalf, and there is nothing for us to be certified about on your behalf either.

And the number, because you will ask for it and because publishing it is the point: Provisa is at 0.1.0a479, pre-1.0. 1,599 requirements complete and 84 in progress, counted on 14 October 2026. Every capability on this page names the requirements behind it and their status is in the repository you can read before you talk to us.
