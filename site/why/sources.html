Provisa / Why / Sources
Connectivity

72 source types. What gets copied follows from what the engine can reach.

Provisa registers sources by type — relational databases, cloud warehouses, APIs, files, graph stores, streams, SaaS systems — and the federation engine decides whether it can read each one in place or needs a replica. Change the engine and the split changes with it.

01 Execution model

Five routes, chosen by what the engine can do.

Every query ultimately executes through the federation engine. Sources fall into five execution paths based on their connectivity.

01
Direct-capable PostgreSQL, MySQL, MariaDB, SingleStore, SQL Server, Oracle, DuckDB Single-source queries execute via the source's native driver (sub-100ms), bypassing the federation engine. The source retains full connector support and participates in federation when joined with others.
02
Federation only Redshift, Druid, Exasol, Hive, Iceberg, Delta Lake Always queried through the federation layer. No direct driver exists.
03
Direct-read (replica) Snowflake, Databricks, ClickHouse A DirectDriver reads from the warehouse natively (Arrow-native where available), lands a replica into the active engine's materialization store, and queries run against that replica.
04
Direct (no cross-source connector) Athena A DirectDriver runs single-source statements whole in the source — every filter, column and limit is pushed down. When a statement joins the source with any other, the driver reads the data and lands a replica; the join runs against that replica. No Trino connector exists for these sources.
05
Materialize → Federation REST/OpenAPI, remote GraphQL, gRPC, Neo4j, SPARQL, WebSocket, RSS, CSV, SQLite, Parquet, and 12 more, including the Enterprise SaaS connectors No federated connector. Provisa fetches their data (on startup or at query time) and caches it as Parquet in S3 or in PostgreSQL, making it reachable by the federation engine for cross-source queries.

03 Wire protocols

Wire-compatible databases need only registry entries.

PostgreSQL and MySQL wire families

CockroachDB, YugabyteDB and Greenplum reuse the PostgreSQL wire; TiDB rides the MySQL wire. They use a base wire's JDBC driver, native async driver and dialect, so they need only registry entries, no new connector code.
04 Partial federators

Snowflake, Databricks and BigQuery.

Snowflake

Reads via snowflake-connector-python, lands a replica into the active engine's store. account, warehouse and role are set in federation_hints.

Databricks

Reads via databricks-sql-connector (Cloud Fetch, Arrow), lands a replica. http_path required in federation_hints.

BigQuery

No DirectDriver; reaches via the federation engine or BigQuery engine ATTACH.
BOTH ROLES Each of these can also be the engine. As an engine it is a partial federator: it executes, and what it cannot reach natively lands in it first. As a source it is read like any other, and lands a replica into the active engine.
05 Athena

Single-source pushes everything. Cross-source lands a full replica.

Amazon Athena is a serverless query service over data in S3, billed per byte scanned. A statement on Athena's tables alone routes directly to Athena: filters, column lists and LIMIT are pushed down, so only the bytes Athena needs to answer that statement are scanned and billed.

CROSS-SOURCE A statement that joins an Athena table with any other source lands a full replica from Athena first — the whole table is read, and Athena bills it — then the join runs against that replica. The source's Replicate and load-protection settings govern how often a landing runs.
athena.yaml
- id: analytics-athena
  type: athena
  database: my_glue_database
  username: ${env:ATHENA_ACCESS_KEY_ID}
  password: ${env:ATHENA_SECRET_ACCESS_KEY}
  federation_hints:
    region: us-east-1
    workgroup: primary
    s3_staging_dir: s3://my-bucket/athena-results/
06 APIs

OpenAPI, GraphQL, gRPC — materialized, then queryable.

OpenAPI

An OpenAPI 3.x spec. Provisa reads the spec, offers each GET operation as a table and each other operation as a command, and caches the responses for a configurable TTL. Authentication is set at registration.

GraphQL

A remote GraphQL endpoint. Provisa introspects the schema, reads through queries, and caches the result. Static headers and client-header forwarding are set in the source mapping.

gRPC

A gRPC service. Provisa discovers the service through server reflection, calls it, and caches the responses.
07 Configuration

Register a source with type and connection details.

Name a type, give connection details. Provisa checks the connection before it saves anything, and the source is live without a restart. Connecting a source exposes nothing — a table is queryable only after someone registers it.

provisa.yaml — Snowflake source
sources:
  - id: my-snowflake
    type: snowflake
    host: org.snowflakecomputing.com
    username: svc_provisa
    password: ${env:SNOWFLAKE_PASSWORD}
    federation_hints:
      account: myorg-myaccount    # required — Snowflake account identifier
      warehouse: COMPUTE_WH       # optional — virtual warehouse to use
      role: PROVISA_ROLE          # optional — Snowflake role
