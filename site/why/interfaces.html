Interfaces

Seven listeners. Sixteen surfaces. No new client library.

Every surface compiles to the same statement against the same model, so the answer does not depend on how you asked. Translation belongs to the compiler, not to the protocol you connected with — pgwire, Flight, GraphQL and the rest produce the same SQL for the same question.

FIG. 01
01 The matrix

What listens, and what rides on it.

Provisa runs seven server listeners, each binding its own port. HTTP, gRPC and Arrow Flight start by default. pgwire, Bolt, Airport and MCP have no default port — they are off until you set one, which is a sentence worth reading twice because it is the one that otherwise costs you an afternoon. Fifteen client-facing surfaces ride those seven. We show the mapping rather than a flat count, because a flat count is the kind of number a reader checks, and because seven is structural — you can verify it from app_startup — where any count of surfaces is a taxonomy someone chose.

Provisa's seven server listeners, whether each one starts by default, and the client-facing surfaces each one carries
Listener Default Carries What connects
HTTP on, 8000 GraphQL · REST / JSON:API / OpenAPI · SQL · Cypher · WebSocket · SSE · Python client Everything with an HTTP client. GraphQL is the canonical schema — REST, JSON:API, OpenAPI and gRPC are derived from it
gRPC on, 50051 A per-role generated proto Typed clients, with an HTTP proxy for those that cannot speak gRPC
Arrow Flight on, 8815 Flight SQL · ADBC · JDBC Columnar consumers, and the Provisa JDBC driver, which moves results as Arrow over Flight
pgwire off until you set a port; 5439 by convention SQL only psql, DBeaver, Tableau, Superset, anything with a Postgres driver
Bolt off until you set a port; 7687 by convention Cypher Neo4j Browser, Bloom, cypher-shell, the official Neo4j drivers
Airport off until you set a port DuckDB attach DuckDB attaches to Provisa as a catalog. Its own listener, not a rider on Flight
MCP off until you set a port; 8009 by convention Governed tools for agents Streamable HTTP at /mcp on its own port — not a path on the API port

That is fifteen surfaces inbound. The sixteenth goes the other way: a governed change stream out to a Kafka topic, carrying the same row filters and masks as a read. Calling an egress stream a “way in” is how a previous draft of this page got to seventeen.

The default ports above are the values in provisa/core/settings_catalog.py (REQ-1913). The conventional numbers for the four opt-in listeners are what every deployment path Provisa itself ships sets — the Helm chart (REQ-1258) and config/provisa-install.yaml — not product defaults. There is a difference and this page keeps it.

02 Honesty first
Governance is uniform. Whatever you connect with, the request becomes the same canonical governed statement under the same role. Row filters, column masking, domain reach and the join guard do not vary by protocol.
Command invocation is not. Registered commands reach GraphQL, pgwire SQL and REST. They do not yet reach MCP, Arrow Flight, gRPC or Cypher over Bolt. If your integration depends on calling a registered command, check this list before you pick a transport.
03 Per surface

The thing you would otherwise find out in week three.

Per-role generated schema. Filtering, ordering and pagination follow the Hasura convention. Apollo automatic persisted queries are supported. GraphQL is the canonical surface the others are derived from.

PostgreSQL-compatible SQL against the model’s names, not the physical tables. POST /data/sql/explain returns the engine’s own annotated plan for the governed statement, with the optimizations that fired. The route that returns governed SQL takes GraphQL, not SQL, and it is POST /data/compile — see the two-route table below.

Simple and extended query protocols, multiple statements, positional and binary parameters, cursors and COPY. SCRAM-SHA-256. DBeaver browses through the usual catalog queries. The listener is off until you set a port — it is not open by default. SQL only, never GraphQL or Cypher, and definitions are not accepted over the wire.

Neo4j Browser, Bloom, cypher-shell and the official drivers run Cypher. Each of your roles appears as a database.

Batch-by-batch streaming, so a full result never sits in memory. Flight SQL and ADBC clients connect. On a Trino engine the route goes through a Flight SQL proxy, and if that proxy is down the request fails rather than silently taking another route. We would rather you got an error than a different execution path.

DuckDB attaches to Provisa as a catalog. Each role sees only its own registered columns, and writes are held in a transaction until commit.

A proto generated per role, showing only that role’s tables and columns. The role is selected by a metadata key on the call, and field numbers stay stable across regenerations.

Governed tools for agents: an agent discovers the catalog and runs queries under the identity behind its token, so it can never do more than that person could. Transport is streamable HTTP, at /mcp on the MCP listener’s own port. stdio is not native — it is the bundled mcp-proxy bridge, and the bridge command is set only by the native launcher, so on the container tier you supply your own. On by default only in the desktop build, bound to loopback — a server deployment turns it on deliberately.

WebSocket and SSE, with the same row filters and masking applied to events as to a read.

A governed change stream out to a Kafka topic, filtered and masked like a read. This one is still being finished — the subscription surfaces above are complete; the sink is not.

pgwire, Flight SQL and gRPC receive rows as the engine produces them. Oversized results are written to object storage and returned as an expiring presigned link; Parquet and ORC are written by the engine straight to the store, so the data never passes through Provisa.

Objects are defined in the model, not by SQL, so CREATE, DROP, ALTER and TRUNCATE are refused on every surface. Semantic SQL has no array, struct or map type; nested data comes back as JSON.

Relationships are joins between tables, so they carry no stored properties, cannot be written, and DETACH DELETE is refused. Shortest paths and variable-length patterns compile to recursive queries with a maximum hop count. GDS analytics and the APOC ecosystem are Neo4j’s, not ours.

04 Connect

Four transports, four snippets.

Two of these four listeners are off until you give them a port. Each snippet sets it, so none of them is a line you can copy and then wonder why it refused the connection.

# The Postgres listener has no default port. 5439 is what our
# Helm chart and installer set; any free port works.
PROVISA_PGWIRE_PORT=5439 provisa run

# In another shell
psql "postgresql://analyst@provisa.internal:5439/provisa"
# Bolt has no default port either. 7687 is the convention,
# set by PROVISA_BOLT_PORT before the server starts.
from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://provisa.internal:7687",
                              auth=("analyst", PASSWORD))
with driver.session(database="analyst") as s:   # the role is the database
    for r in s.run("MATCH (c:Customer)-[:PLACED]->(o:Order) "
                   "WHERE o.total > 1000 RETURN c.name, o.total"):
        print(r["c.name"], r["o.total"])
# Flight is on by default, on 8815.
import adbc_driver_flightsql.dbapi as flight_sql

conn = flight_sql.connect("grpc+tls://provisa.internal:8815",
                          db_kwargs={"username": "analyst",
                                     "password": PASSWORD})
tbl = conn.cursor().execute(
    "SELECT * FROM orders WHERE total > 1000").fetch_arrow_table()
curl https://provisa.internal/graphql \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"query": "{ orders(where: {total: {gt: 1000}}) { total customers { name } } }"}'
04b Compile and explain

Show me the SQL you would run.

Both of these exist, both are useful, and merging them is the mistake. One returns the governed statement with filters and masks inlined, and it takes GraphQL. The other returns the engine’s plan for the statement, and it takes SQL.

The compile route and the explain route compared
You want Route You send You get back
The governed SQL that would run, with row filters and masks inlined, plus the route, the parameters and the enforcement metadata POST /data/compile A GraphQL document Compiled SQL, and an enforcement object that names every filter and mask by field
The engine’s own plan for the statement that would run POST /data/sql/explain SQL An annotated EXPLAIN tree and the optimizations that fired

There is no SQL-in, SQL-out compile route. The role on both comes from the authenticated session.

05 Per role

Four schemas, generated. Not one schema, filtered.

Generated, not filtered

The GraphQL SDL, the SQL information schema, the Cypher label catalog and the gRPC proto are each generated for the role asking. A table a role may not see is absent, not hidden — structurally unreachable rather than denied on request.

Which means your tools are honest

DBeaver draws the schema it was handed. Provisa answers the usual catalog queries from the model and reconstructs primary keys, unique constraints and composite foreign keys, so the tool draws the diagram and suggests joins — within what the role may see, and without knowing anything was left out.
ON HASURA V2? Hasura v2 metadata imports directly — sources, relationships and permissions convert to Provisa configuration. Filtering, ordering and pagination follow the v2 convention your queries already use, and the naming convention can be set to match v2’s, so your client code does not move.
06 Ceilings

What a role is allowed to cost.

01

Rate

Each role has its own request-rate limit, plus caps on concurrent subscriptions and Flight streams. Natural-language queries have a separate limit because they cost model calls. State lives in Redis, so any number of stateless containers share one count, and a stream over its limit waits for a free slot rather than failing.
02

Time and rows

Roles carry ceilings on how long a query may run and how many rows it may return. A role without the right to full results gets a sample, and when a read is cut short the response says so rather than looking complete.
03

Concurrency at the source

Each source can cap its concurrent live reads, so an operational database is not overwhelmed by the analytics team. Asynchronous queries run on their own connections.
