Provisa / Data residency
Data residency

One model. Every region a collection of its own.

The platform never places a copy of a table outside the region you named, and every read, from anywhere, carries the reader's rules. What crosses a border is what you wrote a rule to allow.

One shared model store, every other store its region's own: nodes, engine, replica storage, cache, state, record. A table names a home region. Whole-table copies are built only there; other regions read from that replica under the reader's rules, so what crosses is what the rules allow.

01 The three things it controls

Three mechanisms. One job each.

Provisa controls data residency through three mechanisms and no others: regions, row and column rules, and a home region on a table. Region is not an access dimension — a reader does not inherit a right by being in a region, and an administrator does not administer by region. If an organisation wants a region's tables administered by that region's people, it gives them domains owned by those people.

Regions

One shared model store, and every other store — engine, replica and view storage, cache, state store, record — belongs to a region. A node is launched in a region by a command-line flag; a node started without one, where the platform declares regions, refuses to start and prints the regions available.

Row and column rules

Rules written on user attributes decide what each reader gets. The statement sent to the source already carries them, so a response holds only what that reader was allowed. The filtering happens on the source's side of the border.

Home region on a table

Whole-table copies — a replica or a hot table — are built only in the table's home region. Other regions read from that replica. Naming a home region governs copies, not reads: a home-region table that is not replicated is read live from its source by every region, under the reader's rules, exactly as any unreplicated table is.
02 The regions

One model. Separate clusters.

A deployment may run more than one Provisa cluster off a single model store. The model — every source, table, relationship, role, rule, view, freshness setting and limit — is declared once and is the same for every cluster.

Each cluster is in one region and has its own nodes, engine, storage for replicas and materialized views, cache, state store, record, and address.

A reader connects to a region by its address. What a reader may see is decided by the model's rules on the reader's attributes, the same in every region; where the work is done and where anything is kept is decided by the cluster the reader connected to.

REACH Every source of every region, and every region's stores, are declared in the one model, so any node can reach any of them. The row and column rules decide what it may do with them.
03 What crosses the border

The rules travel with the request. The filtering happens before the border.

Row and column rules written on user attributes — the country a user is in, the role they hold — decide what each request may see. The statement sent to the source already carries them, so nothing a reader may not see is read.

A table that names a home region is served to readers in other regions from that region's replica, read in place under the reader's rules — so the filtering is done in the home region and only what the reader is allowed crosses. Naming a home region governs copies, not reads: a home-region table that is not replicated is read live from its source by every region, under the reader's rules, exactly as any unreplicated table is.

A US node reading an EU-homed table
-- Reader in US queries intake_eu (homed in EU)
SELECT * FROM intake_eu WHERE category = 'public';
-- The US node reads EU's replica in place, with the
-- reader's row and column rules in the statement.
-- Only rows the reader is allowed cross the border.
FAIL CLOSED When the replica has not been built or the home region cannot be reached, the request is refused naming the home region (query.home_region_unavailable). The source is not read live in its place.
04 The home region

What the setting on a table decides.

A table may name one of its organization's regions as its home. Whole-table copies of it — replicas and hot tables — are built only in that region.

What a table's region setting means for whole-table copies and for how other regions read it
Table's region setting Where replicas build Where other regions read it
Names a region (e.g. eu) Home region only From home region's replica, with reader's rules
No region Every region Locally
Draft Nowhere — out of service Not readable

A table with no region is replicated, when its replicate setting calls for it, in the region of the node the reader connected to.

Draft

A table or view set to draft is out of service: neither readable nor writable on any data surface, offered in no schema, and a statement that names it is refused. No copy is built and every copy that exists is removed. It stays editable in the admin, and its owners may preview it in the admin before releasing it.

A move between regions holds no data anywhere in between: the owner sets draft, which removes every copy; the holder of data_residency for the destination sets their region; the owner clears draft. No one needs a grant covering both regions.

05 Views per region

Each region builds its own copy of a view, under its own administrator's identity.

A materialized view is built in every region (unless the view names a region of its own). Each region's coordinator builds its own copy in its own view storage, on the view's schedule.

The build statement is governed — run under the organization's administrator identity, with that node's region as its region attribute. An identity processing within a node carries the node's region.

So each region's copy holds exactly what an administrator in that region may see. When row rules bind to region, the same view returns different rows in different regions. The admin pages say which region's copy a figure came from — an auditor who sees two numbers and no explanation files a finding; an auditor who was told in advance sees a control.

A reader is served from the copy in the region they connected to, with their own rules applied on top.

A VIEW NAMES A REGION For cross-border analytics, build the view inside the region permitted to see the underlying rows and name that region on the view. It is built once there, under that administrator's identity, kept in that region's view storage. Keeping the view's rules consistent with the rules on its tables is the operator's responsibility, as the choice to name a region is.
06 The right to set a region

A right distinct from domain ownership. Compliance can hold it alone.

Setting, changing or removing a table's or view's region requires the data_residency capability, in addition to owning the object through its domain. The same rule applies in the admin and on config import, so the file path is not a way round it.

A grant of data_residency names the values it covers: the organization's regions, and "no region", which is a value of its own, so making an object global is a decision an organization can keep to a few people. Changing an object's region from one value to another requires a grant covering both. While an object is draft, the destination's holder may claim it with a grant covering the new value alone.

The compliance-only grant

An organization can give data_residency to its compliance function alone. Domain stewards manage everything else about an object — its schema, its rules, its freshness, its views — but cannot move its data across a border.

Setting or clearing draft is part of domain ownership and needs no other capability — the three-step move above is a draft from the owner, a region from compliance, and a clear-draft from the owner again.

07 How to try it

Two regions on your machine, Docker-free.

The two-region demo runs two Provisa nodes — one in region eu, one in region us — on the embedded local platform, sharing one embedded Postgres. Each node runs its own DuckDB engine, and a single fakeredis TCP server is the cache.

scripts/launch-demo-regions.sh
# Start the demo (Ctrl-C or --stop to end)
scripts/launch-demo-regions.sh

# Wipe its data dir first, then start
scripts/launch-demo-regions.sh --reset

# Stop everything it started
scripts/launch-demo-regions.sh --stop

Open the eu UI at http://127.0.0.1:8310 and the us UI at http://127.0.0.1:8320 side by side.

What to click

The region selector on Sources, Tables and Cache → Hot

Starts at the node's region. Shows objects homed there plus objects with no region. Switch it, and the list is the other region's.

A cross-region read

On the US node, query intake_eu (homed in EU). The US node reads from EU's replica under the reader's rules, and the admin names the region the row came from.

A data_residency refusal

Log in as resident (eu_resident, grant covers eu and no-region); try to change a US-homed table's region — refused, naming us. Setting the no-region breeds table to eu is allowed, because the grant covers both values the change spans.

The complete walkthrough is in the repository, under docs/regions-demo.md.
