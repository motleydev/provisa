How it works

Provisa is a data kernel.

A compiler and runtime for building your data control plane. Declare a small set of primitives and the whole governed API follows: the query endpoints, the legal join paths, the access rules and the audit trail.

01 The mechanism

A small kernel. Drivers on one side, clients on the other.

The primitives are sources, tables, relationships, terms, roles, capabilities, grants, scope, products and contracts. Every language compiles to one intermediate form. Governance is applied there and pushed down into the native query your engine runs, so a GraphQL query, a SQL statement and a Cypher traversal all pass through the same governance point before anything reaches your data.

01

The kernel

The primitives, compiled. Isolation and permissions are enforced here, once, so no application has to write them again.
02

Drivers

Source drivers, engine drivers and secrets drivers plug in and swap without reinstalling. Provisa drives your systems; it does not run on them and never becomes their engine.
03

Clients

BI tools, notebooks, agents and apps connect over standard protocols. Command bindings answer other tools’ calls.

Provisa compiles each request and hands it to your engine. Results stream back. It scales horizontally and vertically to support your workloads, and the heavy compute is offloaded to the engine you chose.

02 The method, from devops

Ask which primitives would let the solution be assembled, not written.

Operating systems, virtual machines, Kubernetes, Terraform and Helm share a habit. Faced with a problem, they first ask which primitives would let the solution be assembled instead of written. Code stays valuable. It keeps its place behind contracts, for the work the primitives can’t express.

Infrastructure has already made this move. Servers used to be built by hand and kept alive by scripts; today you declare them, and a controller reconciles what runs with what you declared. Data is where infrastructure stood before Kubernetes and Terraform. Each of those tools gave Provisa one idea, and so did a compiler toolkit, LLVM.

Operating systems and virtual machines: a small kernel that enforces isolation

The primitives above are Provisa’s kernel. It enforces isolation and permissions, so governance is compiled into every request. Sources and engines are drivers: you plug them in, and you can swap one without touching the model above it.

Terraform: declare the desired state, and plan before you apply

Your model lives in git branches. A change shows up as a diff, with an impact analysis of everything it touches, and it is approved before it moves from one environment to the next.

Kubernetes and Helm: a control plane that reconciles

What you declared and what is running are kept apart. The model store holds the declaration; the state store holds what the runtime is doing. The runtime keeps converging replicas, freshness and materialized views toward the model, so what you serve follows what you declared.

LLVM: many front ends, one intermediate form, many back ends

GraphQL, SQL, Cypher, SPARQL, gRPC and MCP each compile to one intermediate form. Governance, materialized-view rewrites and optimization run as passes over it, once, for every language. The engines are the back ends that run the result.
03 The bar, from regulated industries

Governance, lineage and stewardship are in the kernel, not bolted on.

Dataops, data management, data architecture and data governance decided which primitives the kernel needed. Highly regulated industries set the bar. Four of their demands are built in.

01

Every answer traceable and reproducible

Citations and run records take you from an answer back to the sources, rules and definitions that produced it.
02

Least privilege by construction

A role reads only what its grants allow, and the compiler applies those grants to every query in every language.
03

Residency by region

Tables, sources and materialized views carry a region. Moving one across a border takes a grant of its own.
04

Review before production

A change reaches production through a merge request, approved by someone other than the person who asked for it.

Both heritages point at one goal: the smallest possible set of primitives with which you can define, secure and operate a data estate.

04 One compiler, every language

Why one compiler can speak every language.

Languages are ways of expressing logic, and the logic of data is bounded: select, join, aggregate, traverse. Transports are bounded too: whatever the protocol, data leaves through a socket as rows, nested documents, graphs, columnar batches or streams. Programming languages have shared one compiler infrastructure for twenty years; Provisa does the same for data.

Building a compiler front end has also become cheap: parser generators like ANTLR and mature open-source parsers for SQL, GraphQL and SPARQL do most of the work, so a new language is a translation into the intermediate form, not a new system. Each request is compiled when it arrives, governed there, handed to your engine as native SQL, and shaped on the way out for the transport that asked.

It also means the pace of change isn’t a constraint. New query languages, protocols, engines and sources keep arriving; for most stacks each one is a migration. Here, a new language or transport is a front end or a shaper, and a new engine or source is a driver: additions to the edges, with the model and its governance unchanged.

05 Command bindings

Does it support the tool you already use? Create its command bindings.

A command is written once, and every language can call it, each under the name that language’s callers expect: that’s apoc.meta.data for a Cypher tool, a catalog function for a SQL client, a field in GraphQL, a tool in MCP. Every command is offered in every language by default. Renaming it or leaving it out of a language is an explicit choice, and SQL is always there because everything compiles to it.

Each one runs governed, so a mimicked tool call never sees more than the role may read. It’s how you teach Provisa any other dialect yourself, without waiting for a release.

CHECK IT The generated SQL is visible for any query in the explorer: write a GraphQL query and the Query Language Explorer shows its Semantic SQL and Cypher translations beside your query, before it runs.
06 What it is not

Not a database. Not your warehouse.

Provisa is a semantic and governance layer that runs on an engine you choose. Your warehouse becomes a replaceable execution engine, not the place your semantics live. Starburst is a query engine; Provisa sits above one and can use it as its engine.
