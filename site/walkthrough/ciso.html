Security briefing · CISO and security architecture

Provisa for Security Leadership

One governed path to your data — for people, applications and AI agents. Policy compiled into every query. No way in that goes around it.

A briefing for the CISO and security architecture provisa.dev

Every new path to data is a new enforcement point

  1. 01BI tools on direct DB credentials. Row filters live in the dashboard, not the data
  2. 02Hand-built APIs and BFF services. Authorization re-coded in each service
  3. 03Pipelines copying data to a warehouse. Every copy needs its own controls and retention
  4. 04AI agents with a database connection. The newest, least-tested path — and the fastest growing

The result

  • Policies drift between paths
  • No single answer to “who saw this record?”
  • Data copies multiply the blast radius
  • Audit means reconciling many logs

Most organizations don't have a data-access policy problem. They have a policy-enforcement-in-too-many-places problem.

The layers — and the exposure each one closes

Layer number Layer What it does Exposure it closes
0 Introspection filtering Hidden tables are absent from the catalog, not discovered then denied Reconnaissance of what exists
1 Public access Anonymous surface must be declared explicitly Accidental public exposure on registration
2 Domain access Roles reach only the domains registered to them Lateral movement across business areas
3 Row-level security Per-role WHERE injection, inherited through views and MVs Over-broad record access via derived data
4 Column visibility & masking Visible, hidden or masked (regex, constant, truncate) PII and secrets in result sets
5 Predicate guard & approval Plan sent to your decision service before execution Out-of-policy queries that pass static rules

New sources, columns and relationships are covered by every layer automatically — nothing to remember to re-apply.

Policy is compiled in, not checked afterwards

Typical: check, then run

  1. 01Query arrives as written
  2. 02Compared against a policy list
  3. 03Allowed query runs as written
  4. 04Any path that skips the check runs ungoverned

Provisa: compile the governed query

  1. 01Identity resolves to a role
  2. 02All the layers are written into the plan
  3. 03Only the governed plan exists to execute
  4. 04Each execution emits its audit row

There is no version of the query that could have run ungoverned — so there is no bypass to find, test for, or monitor.

Even the joins are governed

  1. 01Approved paths only. A JOIN or graph traversal is legal only along a registered, approved relationship.
  2. 02Rejected and logged. Unapproved paths are refused before execution, and the attempt is recorded.
  3. 03Every edge has a reason. Each relationship carries a human- and agent-readable reason it exists.
  4. 04Two keys to opt out. Lifting the join guard needs both a role-level grant and an explicit per-query flag — and RLS and masking still apply.

Why it matters: inference attacks and accidental re-identification usually come from joins nobody sanctioned — not from a single table.

Agents get the same controls as people

  1. 01Scoped identity. Remote agents act only as roles their token's principal holds. Local agents are pinned to a configured role set.
  2. 02Need-to-know. An agent learns its role and that role's purpose — never the rules, masks or grants. Filtered results aren't flagged.
  3. 03Probing is cut off. Naming a role it doesn't hold ends the session and can suspend the principal's token access.
  4. 04Validated queries. Natural-language requests are rate-limited per role before any LLM call, and validated before anything runs.

A data catalog tells an agent what it should do. Provisa enforces what it can do.

Fail-safe by design. Commands marked “requires approval” never run without a hook. You choose allow or deny on timeout, and a circuit breaker isolates a slow decision service.

Probing is treated as an attack

Unheld role requested
From any surface — person, app or agent
Refused
“Not permitted” — no hint whether the role exists
Session ends
Token or principal access suspended
Admin lifts it
No timer — a person decides
Alerted three ways
Admin trail, email to org admins, and your security webhook — with principal, credential, address and transport.
Login throttling
On by default: five failures in five minutes locks the subject out for fifteen.
Complexity and rate limits
Per-role ceilings on query cost and request rate; over-limit queries are refused and logged as policy denials.

Enforced the same way on HTTP, MCP, pgwire, Bolt, Arrow Flight and gRPC.

Least privilege that doesn't decay

  1. 01Grants that expire. Any role grant can carry an expiry date, so temporary access ends on schedule.
  2. 02Unused access removed. Grants unused for a set number of days are removed automatically. The holder and admins are emailed first, and each removal is recorded.
  3. 03Every rule has a reason. Each role and row rule requires a stated purpose, shown next to the rule in access reviews.
  4. 04Attributes, not hand-made grants. Roles derived from user attributes carry no rights and can't be granted by hand. Your org's record overrides the IdP.

Access reviews show what each grant is for — and stale grants clean themselves up.

Lives in your org's own schema, in the store you name per region. Append-only; query text encrypted under your key and shown only to authorized admins.

-- who queried customer data this week?
SELECT c.name, q.actor, q.started_at, q.duration_ms
FROM customers c
JOIN queries q ON q.actor = c.email
WHERE q.started_at > now() - interval '7 days';

Lineage leaves the building too

  • One registration publishes to OpenMetadata, DataHub, Collibra, Atlan, Apache Atlas and OpenLineage
  • Column-level lineage for declared datasets
  • Compiled SQL is readable and exportable

One place answers “who ran what, against which data, and when” — across humans, apps and agents.

Identity comes from your IdP — on every surface

  1. 01Bring your identity provider. OIDC (Okta, Azure AD, PingFederate, Auth0), SAML 2.0, LDAP / Active Directory or Keycloak. With LDAP, a directory removal takes effect before the token expires.
  2. 02TLS 1.2+ and mutual TLS. Every listener speaks TLS 1.2 or 1.3 and refuses older versions. mTLS on pgwire, Bolt, gRPC and Flight can bind the certificate to the user.
  3. 03Least privilege per request. A request acts only as the roles it names; unheld roles are refused by name. Unbound session variables match no rows.
  4. 04Hardened credentials. Personal access tokens stored as SHA-256 hashes, shown once, scoped to one org. Login throttling on by default.

SQL clients, BI tools, Neo4j drivers, Arrow Flight, gRPC and MCP agents all authenticate against the same identity and role model.

Secrets never leak — not even into logs

Secrets

  • Use HashiCorp Vault, AWS Secrets Manager, Google Secret Manager or Azure Key Vault — or the built-in store
  • Built-in store always encrypts; with no key available it refuses to write
  • No API returns a secret value; platform admins can't read an org's secrets
  • Fail-closed: an unresolved reference is an error, never an empty string

Redaction everywhere

  • One redaction rule list per org, on top of built-in rules
  • Applied to OpenTelemetry spans and logs before any exporter — including stdout
  • Applied to audit rows as written and to client-facing errors
  • Every secret Provisa holds or the model references is redacted automatically

Source credentials are references resolved at runtime; engine catalogs and their credentials live in memory only.

Encryption under keys you hold

In transit
  • Every listener: TLS 1.2 or 1.3
  • Helm generates the CA and node certificates
  • Engine node-to-node encryption available
At rest, under your key
  • Opt-in: create your org key to turn it on
  • Wraps secrets, encrypted columns and audit query text
  • Uploads, spill and temp files under a key in your own vault
Ephemeral by design
  • Spill encrypted with a per-query key, discarded when the query ends
  • Catalog credentials held in memory only

High-security mode Provisa never handles plaintext: columns are encrypted at the source and decrypted client-side, and data endpoints require a KMS key on every request. Text-oriented surfaces (pgwire, Bolt, MCP) don't start, and the join guard can't be switched off.

Data residency is enforced, not hoped for

01 · Home region
A table names where it lives; only that region builds its replica
02 · Rules applied at home
A reader elsewhere has row and column rules applied in the home region — only permitted rows cross
03 · Refuse, don't fall back
If the home region is unreachable, the request is refused — never silently read from the source
Moves need a grant
Changing a table's or view's region requires a data-residency grant covering both regions.
Region-aware policy
A member's region becomes a pseudo-role that masks and grants can reference; row filters can key on the serving region.

Each region runs its own engine and stores against one shared model and policy set.

Shrink the attack surface: fewer copies of data

  1. 01Query in place. Federation joins across sources without first copying them into a warehouse or a staging bucket.
  2. 02Governed hand-offs. Other teams get a governed result set — not a pipeline and an unmanaged extract.
  3. 03Masked per role. PII columns can be masked per role in every result, on every protocol.
  4. 04Synthetic data. Auto-generated synthetic datasets let teams build and train without touching real PII.
