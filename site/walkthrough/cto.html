CTO briefing · engineering leadership

Build once. Reuse everywhere.

Less to build, less to maintain, and a data architecture you can keep changing.

A briefing for the CTO Provisa · provisa.dev

Four things that change for engineering

  1. 01Stop rebuilding. One registration serves every API, tool and agent. Logic and data products are reused, not re-implemented.
  2. 02Developers move faster. Typed contracts are generated. Test environments with safe data are created in minutes.
  3. 03Ship safely. The model is code in git. Deploys are diffed, approved, pinned and reversible.
  4. 04Architecture keeps evolving. Engines, regions and sources change behind a stable model — with best practices enforced by default.

The ask: nominate one team and one real use case for an engineering pilot, measured on build effort and delivery speed.

What every team rebuilds today

  1. 01A backend-for-frontend per app. Hand-written services that stitch mismatched sources into one response
  2. 02Access rules per service. Row filters and masking re-coded in every API, report and job
  3. 03Pipelines just to join. Copies into a warehouse so two systems can be queried together
  4. 04Metric definitions per tool. Revenue means something slightly different in each dashboard
  5. 05Test data per team. Ad-hoc copies of production, often with PII still in them
  6. 06A new integration per consumer. Separate drivers, SDKs and connectors for BI, apps, data science and AI

Each copy is code to write, test, secure and support — multiplied by every team and every consumer.

Generated contracts replace hand-written services

  1. 01OpenAPI 3.1, generated. REST and JSON:API share one generated spec, so a client generator produces a typed SDK — nobody hand-writes it.
  2. 02gRPC without a build step. The .proto regenerates whenever the model changes: typed query and insert RPCs per table, with streamed responses.
  3. 03GraphQL valid by construction. Per-role schemas with cursor pagination and aggregates, limited to registered relationships.
  4. 04Real-time without plumbing. Subscriptions stream change events from Postgres, MongoDB, CDC or polling — and can fan out over Kafka.

No backend-for-frontend to maintain: the app gets one governed API across sources that don't match.

Performance patterns, built in

  1. 01Smart routing. Single-source queries and writes bypass federation and go straight to the driver. Only cross-source work fans out.
  2. 02Materialized views that rewrite. Queries are rewritten onto a fresh view automatically — even partial join matches. Refresh only when inputs change.
  3. 03Hot lookup tables. Small lookup tables are cached and inlined into queries automatically; pre-joined relationships can be materialized.
  4. 04Declared datasets, no DAG. Declare the dataset and its lineage is recorded. No orchestration DAG to write or babysit.

Patterns teams usually hand-build per project are properties of the model.

Freshness and load become declared policy, not code in every consumer.

Every developer gets a safe environment

  1. 01Branch an environment. A named, isolated copy of the governed model — its own database schema — seeded from the environment it branches from.
  2. 02Model rights, not data rights. The creator can build the model but doesn't get write, full-results or sensitive-data rights by default.
  3. 03Reversible writes. Writes can go to a local change log; reads show them applied, and one reset returns to baseline.
  4. 04Start on synthetic data. A new environment can start on generated data — plausible rows, no production records.

Source connections carry over as references, so environments never copy credentials.

Realistic test data without the PII

Faked on read
Real rows, fake identities. Reads go to the source; only identifying columns (names, emails, IDs) are faked. Always current, nothing copied.
Synthetic dataset
Generated rows, real statistics. Preserves ratios, key uniqueness, fan-out, skew, nulls and correlations. Any scale; same seed, same data.
PII can't slip through
Columns tagged as PII must declare a fake, or the environment or dataset is refused.
Optional differential privacy
Generate under a privacy budget, or redraw rows that sit too close to real ones.
Comparison report
Source vs synthetic profiles side by side, with any unfaked columns listed.

  1. 01Four-eyes on prod. Protected environments turn deploys into proposals; the requester can't approve their own.

For architects: see and shape the model

  1. 01Query Language Explorer. Write GraphQL and see its live SQL and Cypher translations side by side, then open either in its editor.
  2. 02Schema Voyager and graph view. The role-scoped schema as an ER diagram, and the federated model as a live, traversable graph.
  3. 03Relationships editor. Register and approve the legal join paths, with AI-suggested foreign-key candidates to review.
  4. 04Start from existing models. Import from dbt, Cube, Snowflake, Databricks and Hasura; every import is a proposal you review.

Plus column-level lineage and an entities-and-facts modeling form — the model is visible, not buried in code.

For business stakeholders: their language, their tools

  1. 01Business glossary. Subject-matter experts own term definitions and relationships; AI drafts are saved only when confirmed.
  2. 02Metrics defined once. Every tool and language gets the same definition of revenue, churn or margin.
  3. 03Data products. Owned, documented bundles with purpose, terms and quality checks — with sample queries in six interfaces.
  4. 04Ask in plain English. Natural-language questions become governed queries, validated before they run.
  5. 05Tools they already use. Tableau, Power BI and DBeaver over JDBC or the Postgres protocol, plus Jupyter for analysts.
  6. 06Published where they look. Products and lineage go to Snowflake Horizon, BigQuery Analytics Hub, Collibra, Atlan and others.

Business users self-serve on governed data — without new requests to engineering for each question.

An architecture you can keep changing

  1. 01Swap the engine. Embedded → Trino → Snowflake or Databricks with a configuration change; queries and policies stay put.
  2. 02Re-point sources. Move a table from Oracle to Postgres; consumers and catalog lineage don't notice.
  3. 03Scale the same platform. Laptop, Python wheel, Kubernetes or Terraform — one product at every size.
  4. 04Leave if you need to. The model is declarative config in git and the compiled SQL is yours.

Technology choices stop being one-way doors. The semantics, governance and contracts your teams build live above any single engine or vendor.
