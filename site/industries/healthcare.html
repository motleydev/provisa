Industries · Healthcare

Consented research, PHI columns the researcher cannot see, and one audit log across every source.

A researcher queries the patient table and sees only the rows for patients who consented to research. The PHI columns their clinical colleagues see are not in the schema their session is handed. Every query — whether it reads the EHR mirror, the claims warehouse or the research dataset — lands in one audit log, written at the single governed pipeline so no surface can skip it.

Three scenarios on this page: a consented research view that cannot be bypassed by forgetting to add the WHERE; PHI columns a role never sees in its schema; and one audit log across Snowflake, Postgres and BigQuery with what was enforced on the statement, not just what was asked.

FIG. 01
01 Scenario 1 — Consented research

A view a researcher cannot un-consent, because the predicate is in the statement before execution.

"We need a researcher view over the patient table in our FHIR server's API, limited to patients who have consented to research, without the researcher having to add the WHERE each time they ask." That is the question. The answer is a row-level rule the compiler injects — the researcher does not write it, cannot forget it, and cannot see the column that proves it.

Row-level security in Provisa is a per-table, per-role predicate declared once in configuration and injected into every SELECT against that table for that role. It is the WHERE the analyst did not write.

THE REWRITE A researcher role's predicate consent_research = true is injected into every SELECT after compilation and before execution — not added by the analyst remembering to.

The researcher writes the ordinary query. The same question arriving over GraphQL, over the SQL endpoint, over the natural-language endpoint or over pgwire is rewritten at the one pipeline every surface shares; a plan that reaches the FHIR API already carries the predicate.

The source makes no difference. A researcher whose work spans the EHR mirror in Postgres, a Snowflake claims warehouse and a BigQuery research dataset gets the same rule compiled into each statement the engine routes to each source.

What the configuration says

provisa.yaml — the tables block
# Columns are declared with visible_to lists. consent_research is
# carried on the row but visible only to clinician.
tables:
  - name: patients
    source_id: fhir_api
    domain_id: clinical
    columns:
      - name: patient_id
        visible_to: [researcher, clinician]
      - name: diagnosis_codes
        visible_to: [researcher, clinician]
      - name: consent_research
        visible_to: [clinician]
provisa.yaml — the rls_rules block
# The predicate for the researcher role on the patients table.
# Injected into every SELECT at compile time, before execution.
rls_rules:
  - table_id: patients
    role_id: researcher
    filter: "consent_research = true"

The role cannot see the consent_research column, but the predicate evaluates against the raw row, so it still applies. The column is absent from the schema the researcher is handed; the value is still there to be filtered on, on the server, before anything leaves it.

A query for diagnosis_codes returns only rows where the patient opted in.

02 Scenario 2 — PHI columns, per role

The PHI columns a clinician sees are not in the schema the researcher's session is handed.

The same encounters table is used by two roles: a clinician who needs the identifying columns to do their work, and a researcher who needs the clinical columns to do theirs. The clinician sees patient name, MRN and address; the researcher sees diagnosis, length of stay and outcome, and no PHI column at all.

The column permission model holds per column, per role. A column is declared with the list of roles that can see it, and that list is the schema the role is given; there is no "see-but-hide" tier in the result — a column a role is not in visible_to is absent from its schema entirely.

THE SPLIT The researcher role holds query_development and domain access to encounters, but the PHI columns (patient_name, mrn, street_address, zip_code) list only clinician in visible_to.

A hidden column is absent from the schema and catalog. The researcher does not discover mrn and get refused — it is not in the information schema their session queries, not in the catalog their browser renders, and not autocompleted. Layer 0: a column that is not there cannot be queried, autocompleted, or inferred to exist.

The rule holds through subqueries, CTEs, joins and star expansion alike. A SELECT * under the researcher's session returns the clinical columns, not the PHI ones; a CTE that aliases mrn as something else is parsed, resolved, and refused at the name — because the name was never in the role's schema in the first place.

The joined query

A query that joins encounters to lab_results on patient_id enforces both tables' visibility rules in one plan, and the join itself must match an approved relationship. The researcher's schema holds patient_id on both tables; the relationship between them is approved; the plan runs. A join that no approved relationship covers is refused at parse time.

provisa.yaml — the encounters block
# visible_to per column. researcher sees clinical columns;
# PHI columns list only clinician.
tables:
  - name: encounters
    source_id: fhir_api
    domain_id: clinical
    columns:
      - name: encounter_id
        visible_to: [researcher, clinician]
      - name: patient_id
        visible_to: [researcher, clinician]
      - name: admit_date
        visible_to: [researcher, clinician]
      - name: diagnosis_code
        visible_to: [researcher, clinician]
      - name: length_of_stay_days
        visible_to: [researcher, clinician]
      - name: patient_name
        visible_to: [clinician]
      - name: mrn
        visible_to: [clinician]
      - name: street_address
        visible_to: [clinician]
      - name: zip_code
        visible_to: [clinician]

The researcher's SQL still reads SELECT * FROM encounters. What comes back is the five clinical columns, because those are the five in the schema their role was issued.

03 Scenario 3 — One audit log

One record, every source, every surface, every query.

"We need one audit log that answers 'who read PHI in the last 90 days' across the EHR mirror, the claims warehouse and the research dataset. We do not want three logs, we do not want a joined view across three logs, and we do not want the application layer to be what makes it one."

One audit log, written at the single governed pipeline, so no surface can skip it. The record is written where the governed statement is compiled, not where the source is read; a surface that bypassed it would be a surface that bypassed the compiler, and there is not one.

What is written

Every query — whether it reads from Snowflake, Postgres or BigQuery — is logged with: timestamp, authenticated user, role, the tables touched, the surface it came over, status, duration, row count, and what was enforced on the statement. The query text is stored encrypted and never exposed in the queryable views.

The log is queryable through governed views in the ops domain, so compliance can ask "who read PII-tagged patient tables in the last 90 days" in SQL. The answer is a query, not an export.

WHAT WAS ENFORCED The record keeps what was enforced on the statement — the row rules, masks and column rules applied — not just what was requested. "The analyst asked for everything and got what their role allowed" is in the record, by table and by column, as what the compiler did.

A request governance refused lands in the policy-denials view. ops.policy_denials holds every access attempt the policy layer rejected — the role that asked, the table it named, the surface it came over, and the reason. A hidden column is not in the schema at all; a request that tried to name one is a schema error, not a policy denial, and shows up as such.

The 90-day question, in SQL

Who read PII in the last 90 days
-- ops.pii_access is a governed view in the ops domain.
-- It carries every access to a PII-tagged column across every source.
SELECT user_id, role_id, source, pii_column, logged_at
FROM ops.pii_access
WHERE logged_at >= CURRENT_DATE - INTERVAL '90 days'
ORDER BY logged_at DESC;

The view is in the ops domain like any other table, so it carries the same row and column rules a reader's role is subject to on anything else. A compliance analyst who holds the domain reads the log; a researcher does not.

04 Natural language, scoped to the role

A researcher asks in English. The question is rewritten into the three generated languages, each under the researcher's rights.

The natural-language query endpoint is available on the governed pipeline, so a researcher who prefers to ask in English does not fall outside the compiler's reach.

The endpoint is POST /query/nl. The caller is the role; the question is a string. What comes back is the answer and the three generated statements that produced it, so the researcher can see — and the compliance team can audit — what the English became.

THREE LANGUAGES When a researcher asks "show me diabetic patients admitted in the last month", the question becomes SQL, GraphQL and Cypher, and each runs under the researcher's rights with the same governance as any query — row filters included.

The prompt the natural-language service is handed is scoped to the role's visible schema (REQ-356). A table outside the researcher's schema is not described to the model, so the model cannot propose a plan that reads it.

The endpoint runs under the asking role's rights. A table outside the role's domain access is rejected before execution, whether the question arrived as SQL or English. The compiler does not care which endpoint produced the plan — it rewrites and checks the same way.

OUTSIDE THE SCHEMA A role without domain access to patients cannot ask about it, in SQL or in English. The model is not briefed on tables the role has no access to; the compiler would refuse them anyway.

05 What Provisa reads

Healthcare data lives where it lives. Provisa reads it where it is.

Healthcare data lives in EHR databases, FHIR and other HTTP APIs, claims warehouses, research platforms and files. Provisa reads relational databases, Snowflake and BigQuery, files on disk or S3, and any HTTP API that publishes an OpenAPI description, as sources.

The same rules reach every source

A row rule or a column rule applies to the researcher's queries whether the data is in a PostgreSQL EHR mirror, a BigQuery research dataset, a Snowflake claims warehouse, or an API registered from its OpenAPI description. The source makes no difference to the rule; the engine routes the governed statement to each.

An API becomes a table

An HTTP source with an OpenAPI description is registered the same way a database is. Its endpoints become tables under the model; their columns carry visible_to lists; a query against them is compiled, routed and logged by the same pipeline that compiles, routes and logs a query against Postgres.
06 The mechanism underneath

The three scenarios above are two mechanisms and one place every surface shares.

Row-level security is per table, per role: a WHERE predicate declared in the model and injected into every SELECT for that role on that table. Column visibility is per column, per role: a visible_to list on the column, deciding which roles' schemas contain it. The researcher's consent_research = true and the researcher's missing mrn are the same mechanism in two places.

Every client path gets the same governance. GraphQL, SQL over HTTP, pgwire, Bolt, Arrow Flight, gRPC — and the natural-language endpoint — all pass through the one compiler that rewrites the statement under the caller's role, and all write to the one audit log that scenario 3 describes. There is no query path that skips either.
