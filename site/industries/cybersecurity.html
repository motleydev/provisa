Industries · Cybersecurity

Security work is a join problem. Provisa is the governed join.

A security team already has the data: a build registry, a cloud inventory, a vulnerability feed, an SBOM, a repository, a quality checker, a log stream. The question is who got to see what, under which rule, when a reviewer asks a month later. Provisa is the governed semantic layer that joins those tables under one set of roles, rules and relationships, and records every query against it.

Every tool a security team runs publishes somewhere: a database, an HTTP endpoint, a file on object storage. Provisa registers each as a source, so a build registry's rows, a scanner's OpenAPI response and an SBOM on S3 are all tables in the same catalog, read with the same SQL, GraphQL or Cypher under the same role.

And every join between those tables — a build to its scan result, a deployment to its image hash, an application to its SBOM — matches a relationship someone registered and a steward approved. A join nobody approved does not run.

01 Scenario one — noncompliant builds

A governed view, in the security domain, that every allowed role may ask.

Publish a governed "noncompliant builds" view in the security domain; any role granted that domain may query it. The view is defined once, flows through the same governance pipeline as a table — row filters, column masks, domain reach, join guard — and is served the same way on every surface.

provisa.yaml — the view, in the security domain
# A governed view. Column visibility and row-level security apply
# exactly as they do on a table (REQ-134).
views:
  - id: noncompliant_builds
    domain_id: security
    sql: |
      SELECT b.build_id,
             b.application,
             b.deployment,
             b.image_hash,
             s.severity,
             s.rule_id
      FROM builds b
      JOIN scanner_results s ON s.image_hash = b.image_hash
      WHERE s.severity IN ('high', 'critical')
    materialize: true
    refresh_interval: 300
    columns:
      - name: build_id
        visible_to: [security_admin, security_analyst, app_team]
      - name: application
        visible_to: [security_admin, security_analyst, app_team]
      - name: deployment
        visible_to: [security_admin, security_analyst, app_team]
      - name: image_hash
        visible_to: [security_admin, security_analyst]
      - name: severity
        visible_to: [security_admin, security_analyst, app_team]
      - name: rule_id
        visible_to: [security_admin, security_analyst, app_team]

Row filters limit each team's role to its own deployments; a role with no filter on the table sees every row. The filter is a predicate written on user attributes and is injected into the SELECT before the engine runs it.

provisa.yaml — row-level filter on the underlying table
# rls_rules, as published. The role app_team sees only rows where
# the deployment belongs to the team the signed-in user is on;
# security_analyst has no filter on this table and sees them all.
rls_rules:
  - table_id: builds
    role_id: app_team
    filter: "deployment = current_setting('provisa.user_team')"
ONE PLACE TO POINT A reviewer asks "who could see which noncompliant builds, under which role, last Thursday" — the view is one entry, the row filters live beside it, and the audit record names the role and the surface each query came in on.
02 Scenario two — cloud inventory against policy

One set of tables for every cloud, joined to policy by a relationship a steward approved.

Azure, AWS and GCP inventories register through the cloud inventory source — one set of tables for compute, storage, Kubernetes clusters, databases, networks, IAM, container registries and security groups, with a cloud_provider column that names the cloud a row came from.

The cloud inventory source — tables and the cloud_provider column
Table What it holds
compute_resources VMs and instances across every connected cloud
storage_resources Object stores, disks and file services
kubernetes_clusters Managed clusters by name, region and version
database_resources Managed databases, with engine and version
network_resources VPCs, subnets and routing entries
iam_resources Roles, policies and bindings
container_registries Registries, their regions and their access
compute_security_groups Firewall rules bound to compute resources

Alongside the inventory, policy tables declare what each resource type must comply with: an encryption rule for storage, a public-exposure rule for compute, a tagging rule for every resource type. The policy tables are joined to the inventory through an approved relationship — a steward on the security domain and a steward on the inventory domain each said yes.

A data-quality checker — Soda Core or Great Expectations — registers as a source. It scans the governed view through pgwire, and each check result lands as a row on the source's cadence, governed like any other table. The checker is not a subsystem bolted on the side — it is a source that inherits lineage, freshness, row-level security and the audit record from the layer it reads.

provisa.yaml — the compliance view, refreshed on a schedule
# A materialized view (REQ-135). target_catalog and target_schema
# name where the engine lands the CTAS result; refresh_interval is
# the schedule in seconds.
materialized_views:
  - id: mv-policy-compliance
    source_tables: [compute_resources, encryption_policies]
    join_pattern:
      left_table: compute_resources
      left_column: resource_id
      right_table: encryption_policies
      right_column: resource_id
      join_type: left
    target_catalog: postgresql
    target_schema: mv_cache
    refresh_interval: 300
    enabled: true

The audit log records who queried the violation tables, under which role and over which surface. It does not record which violations came back — the query text itself is not stored in the clear and the record is of access, not of answers.

THE JOIN IS THE PRODUCT The scanner, the inventory, the policy register and the checker are all four someone else's software. The sentence "which compute resources violate which policy, on which cloud, right now" is a join across them — and that join is what the semantic layer makes answerable in one query.
03 Scenario three — CVE × deployment

The SBOM is a file. GitHub is a source. The CVE view is three questions, one per language.

SBOM exports and scanner outputs register as file sources — JSON, CSV or Parquet, local or on s3:// — and a scanner that publishes an OpenAPI description registers as an API source. There is no SBOM or CVE connector shipped: these are the customer's files, and registering them is the configuration step.

The SBOM is joined to the deployment inventory through an approved relationship on application name or image hash. Which key is right is the organisation's choice; the relationship catalog declares it and the steward on each domain approves it, and SQL and Cypher check every join against that record at compile time.

GitHub registers as a source with a personal access token; the steward registers the repository and commit tables wanted, so commit SHAs link builds to their repositories. The source form asks for the token and nothing else; adding the source registers no tables on its own, and a steward picks the ones the organisation needs.

provisa.yaml — the GitHub source and a steward-registered table
# The source form takes the token and nothing else (REQ-1923).
# The steward registers the tables wanted — nothing arrives by
# default.
sources:
  - id: gh-prod
    type: github
    access_token: ${env:GITHUB_PAT}

tables:
  - source_id: gh-prod
    table: commits
    domain_id: security

A materialized view lists CVEs by application, severity and deployment, refreshed on a schedule or when a freshness probe finds the vulnerability feed or the deployment registry has changed. The probe is the published mechanism; the schedule is the fallback when the probe is not configured or the upstream exposes no change signal.

The same question is asked in whichever of three query languages suits the caller — SQL on pgwire, GraphQL on HTTP, Cypher on Bolt — and the row filters, column masks and join guard apply the same way on each, under the role that arrived.

-- Critical CVEs for every active deployment of my applications
SELECT a.application,
       d.deployment,
       c.cve_id,
       c.severity
FROM applications a
JOIN deployments d ON d.application = a.application
JOIN sbom_components s ON s.application = a.application
JOIN cves c ON c.component = s.component
WHERE c.severity = 'critical'
  AND d.status = 'active';
{
  applications {
    application
    deployments(where: { status: { _eq: "active" } }) {
      deployment
    }
    sbom_components {
      component
      cves(where: { severity: { _eq: "critical" } }) {
        cve_id
        severity
      }
    }
  }
}
MATCH (a:Application)-[:HAS_DEPLOYMENT]->(d:Deployment),
      (a)-[:LISTS]->(s:Component)-[:HAS_VULNERABILITY]->(c:CVE)
WHERE c.severity = 'critical' AND d.status = 'active'
RETURN a.application, d.deployment, c.cve_id, c.severity
04 The lane

The scanners, the patchers and the alerters already exist. We are the join across them.

Provisa does not scan infrastructure, patch systems or raise alerts. It is the governed join across the tools that do — and it reads what they write, Splunk and log files included, as tables. The source list already names Logs and Splunk; a log stream becomes rows on a cadence, under the same roles, rules and record as every other table.

What Provisa is

A semantic and governance layer: one model over your security tools, three query languages generated from it — SQL, GraphQL, Cypher — and one append-only record of who asked what, under which role, on which surface. The engine stays yours.

Why it stays in its lane

Not positioning — construction. There is no scanning subsystem to drift out of lane, no patching service to grow, no alert pipeline that would need its own policy engine. The product is one compiler and one governance pipeline; the scanners and alerters stay the tools you already run.
05 How the governance reaches here

The six mechanics the three scenarios all rely on.

Every join is an approved relationship

Every join between security sources is a relationship declared and approved by a steward holding the relationship right in each domain it touches. A join nobody declared does not compile; a join one side approved and the other did not is refused with V002, naming which domain is missing the yes.

Row-level security on user attributes

A row filter is a predicate injected into every SELECT on the table, and it may read attributes of the signed-in user — the team they belong to, the deployments they own, the region they are in. The same predicate applies on SQL, GraphQL and Cypher without being written three times.

The audit log is a table

Access records are queryable through SQL on pgwire, GraphQL and Cypher under the same domain access, row-level security and masking rules as any business table. The reviewer asks "who touched noncompliant_builds last week, with what row count, and what the enforcement object said" — in the same language, under their own role.

Compliance summaries, in materialized views

Materialized views compute compliance summaries — noncompliant builds, failing policies, open CVEs per application — on a schedule, or when a freshness probe finds the upstream changed. The view is a governed object; the schedule and the probe are what keeps it current.

History, for the past audit

A compliance view that declares history keeps every version of its rows. A past audit is re-run as of its date, and as recorded then, with two request headers — X-Provisa-As-Of and X-Provisa-As-Recorded — so a later correction to the data does not change what the auditor saw.

Plain language, three languages generated

A question in plain language is turned into SQL, GraphQL and Cypher. The model sees only the schema the asking role may see, and every generated query runs under that role's rights — the same row filters, column masks and join guard the role carries everywhere else.
06 The six surfaces

Six surfaces answer the same question, under the same role.

One semantic model, six wire surfaces generated from it. The row filter on builds and the join guard on sbom_components → cves hold on each, because the enforcement happens at the compile step every surface passes through — not seven times, once.

PostgreSQL wire protocol

SQL on pgwire for the tools and drivers that already speak Postgres. The Provisa JDBC driver is the same wire — a Java client connects as if it were a Postgres database.

GraphQL

The schema the gRPC, JSON:API and OpenAPI schemas are generated from: an SDL per role, nested selections, and the row filters and masks compiled into the resolver before the engine runs anything.

gRPC

A proto generated per role, so the services and messages an unauthorised client sees are the ones they may call. The enforcement is the same compile step as every other surface.

REST, JSON:API and OpenAPI

A REST surface and a JSON:API surface, with an OpenAPI description generated from the model — endpoints a reviewer can read before any code calls one.

Arrow Flight

Columnar reads over Flight for the analytics clients and notebooks that prefer Arrow over a row cursor. The same role, the same filters, the same record.

MCP for AI agents

An MCP server exposes the model to an AI agent — and every tool call is scoped to the capabilities of the identity behind it. An agent cannot discover a table its caller may not see, because the schema handed to the agent is the caller's.
07 How to run it

One command, Python 3.12, and the API and the web UI are up.

pip install "provisa[embedded]" then provisa run — no Docker, no Node, no external services; Python 3.12. One command starts the API and the web UI. Connect your build registry and patch baseline as sources, join them, and query the result.

The first five minutes
# A fresh virtualenv, then the embedded tier.
pip install "provisa[embedded]"

# Starts the API server and the web UI in one process.
# Everything else — the engine, the control-plane store, the
# cache — is embedded. No external services to run.
provisa run
