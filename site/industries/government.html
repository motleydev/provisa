Industries · Government

Multi-agency work is a join problem. Provisa is the governed join.

An agency keeps the data: a case record, an intelligence report, a shared federal series, a policy table. The question is who may see which column of which row, under which role, inside which domain, and what the audit record names when a reviewer asks later. Provisa is the governed semantic layer that answers it from one model.

Every column names the roles that may see it. Every row filter is injected before the engine runs the statement. Every table lives inside a domain, and a reference out of that domain is refused by name. Every table may name a region, and whole-table copies live there. Every governed query lands in an append-only audit log, written at the single pipeline every surface goes through.

01 Scenario one — multi-agency data isolation

An intelligence report is shared across analysts, and only cleared roles see the source details — on every row the clearance allows.

Every column on the report names the roles that may see it. A role that is not on the column's visible_to list does not see the column, in any query — the field is absent from the schema the role is handed, not blanked out at the end of a result set.

01

Three tiers of column visibility

A column is public (served to every role), restricted (served to the roles its visible_to list names), or hidden (absent from the schema altogether). One column list, three visibility rules per column.
02

What a role cannot see, it cannot discover

A hidden column cannot be queried, autocompleted, or inferred to exist. The schema the role receives is the schema the role may read; there is no "see the field, not the value" in-between.
03

A row filter narrows the rows a role sees

A row filter is a predicate written on user attributes and the row — the role's clearance against the row's classification, the role's agency against the row's owner. The predicate is injected into every SELECT on the table, before the engine runs it.
04

A role with no filter on the table sees every row

The rules list is explicit: where a role is named with a filter, that filter applies; where a role is not named, no filter applies and the role may see every row.
05

The record names the role and the surface

The read lands in the audit log alongside the user as the identity provider asserted them, the role they assumed, the table and the surface — SQL on pgwire, GraphQL over HTTP, Cypher on Bolt. The query text is stored as a hash, never in the clear.
provisa.yaml — classified columns and a clearance filter
# A reporting table. The source_details column is restricted
# to cleared roles; the headline and classification are visible
# to the wider analyst pool. visible_to is the published form
# on columns (docs/security.md § RLS lines 280-283).
tables:
  - id: intelligence_reports
    source_id: core_intel
    domain_id: intel
    columns:
      - name: report_id
        visible_to: [analyst, secret_analyst]
      - name: headline
        visible_to: [analyst, secret_analyst]
      - name: classification_level
        visible_to: [analyst, secret_analyst]
      - name: source_details
        visible_to: [secret_analyst]

# A row rule on the table, in the top-level rls_rules list
# (docs/security.md § RLS line 277; docs/configuration.md line
# 835). The analyst role sees only unclassified rows; the
# secret_analyst role sees the SECRET rows too.
rls_rules:
  - table_id: intelligence_reports
    role_id:  secret_analyst
    filter:   "classification_level = 'SECRET'"

02 Scenario two — public data catalog federation

Two agencies share one federal catalog, and neither sees the other's operations table.

A domain is a permission boundary. A role reads freely inside the domains it is granted and needs an explicit grant for any other. One agency's operations lives in one domain; the other agency's lives in a second; the federal catalog lives in a third that both are granted.

01

A table carries its domain_id

Every table names the domain it belongs to. The domain is not a label the catalogue shows — it is the primary key the governance pipeline reads to decide reach. Change the domain_id and the reach changes with it.
02

A role carries its capabilities and its domain_access

A role declares two things: a list of capabilities, such as query_development, and a list of domains it may reach. Roles compose through inheritance; the effective domain_access is the union of the role and its parents.
03

The domain grant is both a visibility boundary and an execution boundary

The published model hides first: a table in a domain the role was not granted is absent from the role's schema (Layer 0). Then it refuses: a reference to a table outside the role's reach is rejected before execution (Layer 2). One grant, two layers of the same rule.
04

A relationship is served when both ends are

A join between two tables is a relationship between two columns. A relationship is served to a role when both of its ends' columns are visible to the role; one end hidden hides the relationship, and a hidden column cannot be autocompleted or inferred to exist.
05

A cross-domain reference is rejected before execution

A query that names a table outside the role's granted domains does not run. The refusal happens before the engine opens the plan; no data is read, no row count leaks, no shape of the refused table is revealed.
provisa.yaml — two agencies and one shared federal catalog
# An agency table lives in its own domain. domain_id is the
# published key (docs/configuration.md line 555), not "domain".
tables:
  - id: agency_a_operations
    source_id: core_a
    domain_id: agency_a
  - id: agency_b_operations
    source_id: core_b
    domain_id: agency_b
  - id: fedregister_rules
    source_id: govdata
    domain_id: public_registers

# A role declares capabilities and the domains it may reach.
# The agency A analyst has operations in agency_a plus the
# shared public_registers domain — nothing in agency_b.
roles:
  - id: agency_a_analyst
    capabilities: [query_development]
    domain_access: [agency_a, public_registers]
  - id: agency_b_analyst
    capabilities: [query_development]
    domain_access: [agency_b, public_registers]
The refusal, when agency A references agency B
# A query from agency_a_analyst that reaches into agency_b.
# The error shape is the published one (docs/api-reference.md
# line 1209). Code V000; the message names the table and the role.
{
  "code":    "V000",
  "message": "Table 'agency_b_operations' is not accessible for role 'agency_a_analyst'"
}

03 Scenario three — regions and residency

One deployment, many regional clusters, one shared model.

Provisa runs as region-specific clusters off one shared model — each cluster has its own nodes, engine, replica storage, cache and record. The model and the roles are defined once; the clusters are the thing that lives in each place the data has to.

01

Whole-table copies live only in the home region

A reader in another region is served from that replica with their own row and column rules applied on the home side. If the home region cannot answer the request, it is refused by name — there is no fallback across the border.
02

A table's region pins its copies to one cluster

Set region on the table and whole-table copies are built and refreshed only on that region's cluster. The attribute lives on the table in configuration; it is the one place a reviewer looks to see what is pinned where.
03

A view that names a region is built only there

Replicas are built only in the home region. A materialized view that names a region is built and refreshed only there; one that names none is built in every region. The deliberate declaration is the view that names the permitted region.
04

What crosses the border is decided by rules — and the right to move it is held separately

What crosses a border is decided by row and column rules, and a materialized view that names a region is the deliberate declaration of what may leave. The right to move data between regions is data_residency, a capability held separately from org admin.
provisa.yaml — a table pinned to a region
# The region on the table is the key the governance pipeline reads
# to decide which cluster's storage holds the whole-table copies.
tables:
  - id: case_records
    source_id: core_records
    domain_id: agency_a
    region: us

# A view that names the same region, built and refreshed only there.
# A view that named no region would be built in every region.
views:
  - id: case_summary
    domain_id: agency_a
    region: us
    materialized: true
    refresh_interval: 1h
    sql: |
      SELECT jurisdiction, COUNT(*) AS caseload
      FROM   case_records
      GROUP  BY jurisdiction

04 Why a public-sector reader chooses this

One audit record, three ways in, every query accounted for.

The audit row

Every query writes one row: the timestamp, the user as the identity provider asserts them — OIDC, Keycloak or SAML 2.0 — the role assumed, the tables touched, the surface, the status, the duration, the row count, and what was enforced on the statement.

The query text itself is stored as a SHA-256 hash alongside the encrypted body; a reviewer compares hashes to recognise a repeated query, and the clear text is never read out of the queryable ops tables.

The log is a table

The audit log is queryable through governed views in the ops domain, so oversight can ask who read a tagged table in the last 30 days, under which role, over which surface — in SQL on pgwire, in GraphQL, in Cypher, under the same domain access, row rules and masking as any business table.

A second queryable view, policy_denials, records every access attempt governance rejected — the HTTP 401 and 403 responses the surface returned, with the role and the table the request named.

The trace

A request governance refuses is recorded as a policy denial, so an analyst probing for tables outside their grant leaves a trace — the role, the reference, the refusal code, the timestamp. The hidden columns themselves do not appear in the log; a hidden column is absent from the schema the analyst sees, so there is no attempt to refuse.

05 Where the data lives, and how it reaches the team

Whether the data is in a PostgreSQL database, a Snowflake warehouse or a CSV exported from a legacy system — the same rules reach it.

Where it lives

Government data lives in Oracle and PostgreSQL databases, in Snowflake, in S3 data lakes and in CSV extracts from legacy systems. Each registers as a source — a config entry naming the connection, the credentials and the schema — and its tables appear in the catalog under their domain.

Seventy-two source types are published: relational databases, cloud warehouses, data lakes, file sources (CSV, JSON, Parquet, Arrow), API sources (OpenAPI, graphql_remote, grpc_remote), stream sources, a graph source, data-quality checkers — enough that most government data already has a source type for it.

The same rules reach it

A row filter on an Oracle table applies exactly as it does on a PostgreSQL one. A domain grant bounds reach across every source the role may read. The roles and the rules are defined on the model; the connection to the source is what the engine does with them underneath.

The government open-data source, govdata, is one source with sub-schemas per subject — commerce (SEC, patents, CFTC), economy (banking, fiscal, housing, transport), demographics (census), government (Federal Register, FEC) — joined to an agency's own tables through declared relationships.
