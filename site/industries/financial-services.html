Financial services

Governed across borders. Reproducible through time.

Residency enforced by views that name a region, so what crosses a border is what a rule you wrote allows. Views with history replay a regulator's question as it was recorded then, with two request headers. Governed graph queries over your model, with masking. Internal exposures joined to public series — the government open-data source, by subject.

Four worked scenarios on this page. Each is compliance or risk under statutory pressure, and each uses the same model — the sources, roles and rules declared once and enforced on every surface.

01 Scenario — residency

A bank in Switzerland and Germany. Swiss client rows stay in Switzerland, and Frankfurt still sees deposits by canton.

The group runs regulated subsidiaries in two countries. Each must keep client records on its own territory. Group finance in Frankfurt still needs the aggregate — deposits by canton — to roll up the balance sheet.

01

The client tables name their region

The Swiss client table names ch as its home region; whole-table copies of it are built only in Switzerland. The German client table names de; its copies are built only in Germany.
02

The aggregate view also names ch

A materialized view named deposits_by_canton is built and refreshed only in Switzerland. The aggregate is computed inside the country, from the Swiss client rows. A view that named no region would be built in every region, Frankfurt included — so the view must name ch.
03

Frankfurt roles are granted the view's domain, not the client tables'

Row and column rules on the view are written on the reader's own attributes, as on any table. Region is never an access dimension. The client rows are not in the Frankfurt role's schema, because the role has no grant on their domain.
04

The audit log records which region's copy served the read

Every statement writes a row: the regulator who ran the query, the role they assumed, the view they read, and the region whose copy served it. Each organisation's log is kept in each region it selects.
provisa.yaml — Swiss client table, Swiss-homed view, Frankfurt role
# The client table lives in Switzerland.
tables:
  - name: clients_ch
    source_id: core_banking_ch
    domain_id: retail_ch
    region: ch
    columns:
      - { name: client_id,  visible_to: [clinician_ch, risk_ch] }
      - { name: canton,     visible_to: [clinician_ch, risk_ch, group_finance] }
      - { name: balance,    visible_to: [clinician_ch, risk_ch] }

# The aggregate view is built and refreshed only in Switzerland.
# Frankfurt reads it from that copy, under its own domain grant.
views:
  - name: deposits_by_canton
    domain_id: group_finance
    region: ch
    materialized: true
    refresh_interval: 1h
    body: |
      SELECT canton, SUM(balance) AS deposits
      FROM retail_ch.clients_ch
      GROUP BY canton

# A row rule on the view, written on a reader attribute.
rls_rules:
  - table_id: deposits_by_canton
    role_id:  group_finance
    filter:   "deposits >= 0"

02 Scenario — regulatory replay

A broker-dealer reproduces a client's positions and the prices used, exactly as they stood at the close eight months ago.

Positions and prices are materialized views that declare history. Every refresh appends versions, never overwrites. Two request headers read them in time: X-Provisa-As-Of answers as of the close on the date, and X-Provisa-As-Recorded answers as Provisa had recorded it then — so a correction made since does not change the historical answer.

curl → the positions view with both time headers
# Positions at the close eight months ago, as recorded then.
curl -H "Authorization: Bearer $TOKEN" \
  -H "X-Provisa-As-Of: 2026-02-28T22:00:00Z" \
  -H "X-Provisa-As-Recorded: 2026-02-28T22:00:00Z" \
  "$PROVISA_URL/views/positions?account=A-7742"

# Prices used to value them, same two timestamps.
curl -H "Authorization: Bearer $TOKEN" \
  -H "X-Provisa-As-Of: 2026-02-28T22:00:00Z" \
  -H "X-Provisa-As-Recorded: 2026-02-28T22:00:00Z" \
  "$PROVISA_URL/views/instrument_prices?date=2026-02-28"
01

Rights, masks and row rules apply as to any read

The time-travel read is a read: the reader's role, their row rules on the view, and the column masks their role is subject to all apply, exactly as on a current-time read. A corrected row recorded today does not change what the as-recorded read returns.
02

The audit record keeps both times

Every statement writes as_of and as_recorded alongside the user, the role, the tables touched and what was enforced on the statement. The whole audit row is encrypted at rest.
03

Regulators verify by re-running the query

The same query, with the same two headers, reproduces the figure. A later correction is visible as a correction — in the as-recorded read, the historical answer is unchanged; in the as-of-only read, the corrected row appears.

03 Scenario — fraud graph

An insurance claim is scored against the links the claimant shares with earlier claims: address, phone, bank account, repair shop, witness.

Claims, policies and payments are modelled once, as tables with approved relationships between them. The Cypher surface walks the model as a graph, from a new claim out to every earlier claim sharing an attribute. Relationships exist as joins between tables, which means they carry no stored properties.

01

A model reads the graph over Arrow Flight; an agent reaches it over MCP

A fraud model consumes the graph by streaming it over Arrow Flight. An investigator's agent reaches the same model through the MCP server; every tool call is scoped to the caller's role, so the agent can never do more than the investigator could.
02

The natural-language job returns SQL, GraphQL and Cypher — the agent takes the Cypher branch

Asked "which earlier claims share anything with this one?", the question becomes SQL, GraphQL and Cypher in parallel. Each runs under the asking role's rights with Stage 2 governance applied. The agent takes the Cypher branch and shows the network of shared addresses, accounts, repair shops and claims.
03

Masked columns come back masked; hidden columns are not in the schema

Masking applies in every query language and every output format: a client name or an account number marked masked for the investigator's role comes back masked in the Cypher result as it does in SQL. A hidden column is absent from the schema the agent sees, however it asks.
Cypher — shared attributes between a new claim and earlier claims
// Walk out from a new claim through its claimant's shared
// addresses, bank accounts and repair shops to earlier claims.
MATCH (new:Claim { claim_id: $claim_id })-[:FILED_BY]->(c:Claimant)
MATCH (c)-[:LIVES_AT|:PAID_FROM|:USED_SHOP]->(attr)
MATCH (attr)<-[:LIVES_AT|:PAID_FROM|:USED_SHOP]-(other:Claimant)
MATCH (other)<-[:FILED_BY]-(prior:Claim)
WHERE prior.claim_id <> new.claim_id
RETURN prior.claim_id,
       collect(DISTINCT labels(attr)) AS shared_kinds,
       count(DISTINCT attr)           AS shared_count
ORDER  BY shared_count DESC;

04 Scenario — concentration

A credit-risk team reads each commercial borrower's exposure alongside its industry's trend and its county's demographics, before the economy turns.

01

Loan exposures from the core banking warehouse, as a source

Snowflake, Databricks, BigQuery or another warehouse registers as a source. Snowflake and Databricks are read through their own drivers into a replica the engine queries; BigQuery reaches through the federation engine.
02

Joined to federal series through the geography linker

The ECONOMY and DEMOGRAPHICS subjects of the government open-data source — the econ, banking, fiscal, census schemas — join to the exposures through the geography linker schema, on industry code and county.
03

A materialized view, on a schedule or on a freshness probe

The concentration view refreshes on a schedule, or when a freshness probe finds the public series has published. Readers see the view, not the join plan.
04

Borrower names masked for every role except credit risk

The borrower-name column carries an ordered masks list. The risk team's role matches a none entry and sees the real value; every other role falls through to the default mask and sees a hashed one.
05

Public figures served as public-scoped columns

The federal trend series are marked with scope public and are served to every role of the organisation; the exposure figures stay restricted to roles visible_to names. One view, two visibility rules per column.

05 Three reasons regulated institutions choose this

Residency. Replay. Public data, governed.

Residency

A table names its home region. Whole-table copies are built only there. A reader elsewhere is served from that replica with their own row and column rules applied before anything crosses. Cross-border analytics is a materialized view that names the permitted region.

FAIL CLOSED If the home region cannot answer, the request is refused by name (query.home_region_unavailable). There is no fallback across the border.

Bitemporal and audit

Views with history answer as of a past time, as it was recorded then. A correction recorded today does not change what the as-recorded read returns.

Every query lands in the append-only audit log: user, role, tables, status, duration, row count, what was enforced on the statement, and the times a time-travel read used.

The log is queryable through governed views in the ops domain, so compliance reviews are ordinary governed queries, over the same surfaces, under the same rules.

Public data, governed

U.S. government open data by subject — commerce (SEC, patents, CFTC), economy (banking, fiscal, housing, transport), demographics (census), government (Federal Register, FEC) and more — registered as one source per subject.

Joined to your own loan, credit or holdings tables through a relationship declared and approved by a steward holding the relationship right in each domain the join touches.

Internal rows stay role-restricted; the federal trend series are served as public-scoped columns. One query, different visibility rules per column.
