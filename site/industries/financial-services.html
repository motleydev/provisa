Industries · Financial services

Four scenarios the regulators ask about, on one semantic layer.

A wealth manager with Swiss client tables Frankfurt may analyse but not read raw. A broker-dealer whose end-of-day positions must still answer the question the regulator asked on the date they asked it. An insurer whose claims investigator wants a graph. A commercial lender joining its loan book to the federal series behind concentration risk. The four stories below are read on one semantic layer, with the reader's row and column rules compiled into every statement before any database sees it.

Three query languages generated from one model: SQL on the Postgres wire, GraphQL over HTTP, and Cypher on HTTP and Bolt. The engine stays yours — Snowflake, Databricks, BigQuery, Trino, DuckDB, ClickHouse or Postgres — and so do the keys. The product is self-hosted; there is no SaaS.

02 Scenario 1 · Views with history

Answer the question the regulator asked, as of the date they asked it.

Positions and prices are materialized views that keep history: every refresh appends versions, never overwrites. X-Provisa-As-Of answers as of the close eight months ago; X-Provisa-As-Recorded answers as Provisa had recorded it then, so a correction made since does not change the historical answer.

A read, point-in-time and as-recorded
# The GraphQL endpoint carries the two headers. The view is the one
# declared with history on; the engine answers from the version
# that applied at as_of, as Provisa knew it at as_recorded.
curl -X POST https://provisa.internal/data/graphql \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Provisa-As-Of: 2026-02-28T21:00:00Z" \
  -H "X-Provisa-As-Recorded: 2026-02-28T22:00:00Z" \
  -d '{"query": "{ positions { account_id instrument_id quantity marked_price } }"}'
The view that keeps history
materialized_views:
  - name: positions_eod
    domain_id: trading
    bitemporal_mode: on
    bitemporal_key: [account_id, instrument_id, trade_date]
    rls_rules:
      - visible_to: [desk_head, compliance, regulator]
    sql: |
      SELECT account_id, instrument_id, trade_date,
             quantity, marked_price, pnl
      FROM positions_source
AS ON ANY READ The same request reads the view as it was recorded on that date, with the reader's rights, masks and row rules applied as to any read. There is no second enforcement path for a time-travel query — the one that governs a live read governs this one.

The two parameters answer two different questions. Answer as of a past time, as it was recorded then. A correction recorded today does not change what the as-recorded read returns.

The audit record keeps both times

Who ran the query, under which role, and both times it read with — as-of and as-recorded. The reviewer who verifies the figure does not have to reconstruct what the system was told; the record carries it. See the views with history reference for the full set of headers and the invariants.
03 Scenario 1b · Residency

Swiss client rows stay in Switzerland. Frankfurt reads deposits by canton.

A table names a home region, and whole-table copies of it are built only there. The Swiss wealth-management client table names ch; the replica is in Zurich; no copy of it exists anywhere else.

A materialized view that names Switzerland as its region is built and refreshed only there — deposits by canton, computed inside the country. A view that names no region would be built in every region, Frankfurt included, so the view must name ch.

The view that names Switzerland
materialized_views:
  - name: deposits_by_canton
    region: ch
    domain_id: ch_analytics
    rls_rules:
      - visible_to: [ch_steward, de_regulator, compliance]
    sql: |
      SELECT canton,
             COUNT(*)            AS clients,
             SUM(balance_chf)    AS total_chf
      FROM client_deposits
      GROUP BY canton
THE DOMAIN GRANT Frankfurt roles are granted the view's domain, not the client tables' domain, so the client rows are not in their schema. Row and column rules on the view are written on the reader's own attributes, as on any table — region is never an access dimension.

What the audit record shows

The regulator who queried the view, under which role, and which region's copy served it. A compliance review that asks "did the Frankfurt read ever materialise a Swiss row outside Switzerland?" answers from the record, not from a screenshot.
04 Scenario 2 · The broker-dealer

The end-of-day the regulator received, re-read on request.

Positions and prices are two views with history over the trading tables (§2 has the mechanism). On a weekday close the engine writes a new version of each; corrections and dividends land as later versions. Nothing is overwritten.

THE VERIFICATION Regulators verify the figures by re-running the time-travel query as of the date. The X-Provisa-As-Of and X-Provisa-As-Recorded headers decide which version is read, and the audit record carries both. No "archive" is unwound and no snapshot is exhumed — the view itself keeps the history.
Re-run eight months later, over pgwire
-- The same statement the desk ran at close. Headers travel on the
-- session (SET LOCAL on pgwire) rather than as HTTP headers here;
-- the two times are the same ones GraphQL uses, written as settings.
SET LOCAL provisa.as_of         = '2026-02-28T21:00:00Z';
SET LOCAL provisa.as_recorded   = '2026-02-28T22:00:00Z';

SELECT desk, SUM(mtm_usd) AS mtm
FROM   positions_eod
WHERE  trade_date = DATE '2026-02-28'
GROUP  BY desk
ORDER  BY mtm DESC;

The reviewer and the submitter read the same view, with the same two times, through the same compiled statement, under the same rights the role carried on the day. The record of the read holds the pair.

05 Scenario 3 · The fraud graph

A claims investigator asks the graph. The agent asks the same graph, under its own role.

The model exposes Cypher over HTTP and Bolt, so the fraud team's Neo4j Browser speaks to Provisa unchanged. Relationships exist as joins between tables, which means they carry no stored properties — a nice property when you want the edge to be the join someone approved rather than a bag of its own.

What the agent can and cannot do

Agents can run Cypher under the caller's role through MCP, so an agent can never do more than that person could. Masks and row rules apply as they do to the investigator; the agent reads the schema the role was given, not a privileged one.
SELECT c2.claim_id, p.address_id
FROM   claims c1
JOIN   policies p1 ON p1.policy_id = c1.policy_id
JOIN   parties  pr ON pr.party_id  = p1.insured_id
JOIN   policies p2 ON p2.insured_id = pr.party_id
JOIN   claims c2  ON c2.policy_id   = p2.policy_id
WHERE  c1.claim_id = '2026-00812';
{
  claim(id: "2026-00812") {
    policy {
      insured {
        policies { claims { claim_id addresses { address_id } } }
      }
    }
  }
}
MATCH (c1:Claim {claim_id: '2026-00812'})
      -[:ON_POLICY]->(:Policy)
      -[:INSURES]->(party:Party)
      <-[:INSURES]-(:Policy)
      <-[:ON_POLICY]-(c2:Claim)
RETURN c2.claim_id,
       [(c2)-[:AT_ADDRESS]->(a:Address) | a.address_id] AS shared
THREE, NOT SIX Asked "which earlier claims share anything with this one?", the natural-language job returns the answer in SQL, GraphQL and Cypher; the agent takes the Cypher branch and shows the network of shared addresses, accounts, repair shops and claims. Three languages generated from one model, not six — the Cypher reference lists the shape the engine produces.

Masked columns — client names, account numbers — come back masked in the graph as they do in SQL, and a hidden column is not in the schema the agent sees, however it asks. The row rule the investigator carries — "only claims in your region, under your authority" — travels on the Cypher path as on the SQL path, because both compile against the same model under the same enforcement.

06 Scenario 4 · Credit concentration

The loan book, joined to the federal series behind concentration risk.

Loan exposures from the core banking warehouse — Snowflake, Databricks, BigQuery or other — registered as a source; Snowflake and Databricks are read through their own drivers into a replica the engine queries. BigQuery is reached through the federation engine.

Joined to federal economic and demographic series from the government open-data source — the ECONOMY and DEMOGRAPHICS subjects — through the geography linker schema. The GovData reference lists the series each subject exposes.

Concentration against ECONOMY series, through geo
-- Loan exposures aggregated by county, joined to the ECONOMY
-- subject's banking and housing series through the `geo` linker.
SELECT g.county_fips,
       SUM(l.outstanding_usd)        AS exposure,
       e.banking_deposits_usd,
       h.housing_units
FROM   loans l
JOIN   geo.counties      g ON g.county_fips      = l.county_fips
JOIN   econ.banking      e ON e.county_fips      = g.county_fips
JOIN   econ.housing      h ON h.county_fips      = g.county_fips
GROUP  BY g.county_fips, e.banking_deposits_usd, h.housing_units;
FRESHNESS A materialized view refreshes on a schedule, or when a freshness probe finds the public series has published. The lending team does not race the federal release calendar; the view does.
The materialized view that follows the publication
materialized_views:
  - name: loan_concentration_by_county
    domain_id: credit_risk
    refresh:
      schedule: "0 2 * * *"
      on_upstream_publish:
        - econ.banking
        - econ.housing
    rls_rules:
      - visible_to: [credit_risk, compliance]
    sql: |
      SELECT g.county_fips,
             SUM(l.outstanding_usd) AS exposure,
             e.banking_deposits_usd,
             h.housing_units
      FROM   loans l
      JOIN   geo.counties g ON g.county_fips = l.county_fips
      JOIN   econ.banking e ON e.county_fips = g.county_fips
      JOIN   econ.housing h ON h.county_fips = g.county_fips
      GROUP  BY g.county_fips, e.banking_deposits_usd, h.housing_units
07 Governance for all four

One governance model under every scenario above. These are the panels that read on the audit.

The four scenarios draw on the same primitives: an ordered masks list on a column, a visibility scope on the column itself, a residency rule on the table, and an append-only audit record that names what was enforced on each statement. None of them is a surface-specific control — they rewrite the statement before any database sees it, on every query path, in every language.

Column masks are an ordered list

A column carries an ordered masks list. The first rule whose visible_to fires wins; if none match, the column reads clear or is stripped by its visibility. One place names what each role sees, auditable per role per column.

Public figures can be public-scoped columns

A column scoped public is served to every role of the organisation; a restricted column is served only to the roles its visible_to names. The deposits-by-canton totals ride on public; the account number rides on restricted with a mask.

Residency is copy control, not read control

A table names its home region, and whole-table copies of it are built only there. A reader elsewhere is served from that replica with their own row and column rules applied before anything crosses. Cross-border analytics is a materialized view that names the permitted region.

Fail-closed by name

If the home region cannot answer, the request is refused by name. There is no fallback across the border. The error carries the region, so the person reading it knows which one did not answer, not that the system is vaguely unwell.

Audit is a governed table

Eight views in the ops domain expose the internal logs — audit, approvals, sessions, views, sources, keys, requests, errors — so the audit trail is queryable like any other table rather than a log file to grep. Governed, so the reader's own rules apply.

Three tiers of visibility

public, served to every role; restricted, served to the roles visible_to names; and hidden, absent from the schema the role is handed. Three tiers, one per column, applied uniformly across SQL, GraphQL and Cypher.

What a query writes to the audit log

The published audit fields for every statement, including the two times a time-travel read used.
Field What it holds
tenant, user, role The organisation, the person and the role they held when the statement ran
query_hash SHA-256 of the statement text
query_text Encrypted statement text
table_ids, table_names Every table the compiled statement touched
source, route Which registered source and which routing decision answered the read
status, duration_ms, row_count Outcome, time, and rows returned
enforced What was enforced on the statement — the masks that fired, the row rules injected, the join approvals
as_of, as_recorded Both times a time-travel read used
logged_at When the record was written

Written at the single governed pipeline, so no surface skips it; the database refuses UPDATE and DELETE against the log by rule, not by application logic that an administrator could route around.

GovData, by subject

U.S. government open data by subject — commerce (SEC, patents, CFTC), economy (banking, fiscal, housing, transport), demographics (census), government (Federal Register, FEC) and more — registered as one source per subject. One connector, one authority registry, the same three-tier visibility and the same ordered masks list as any registered source. See the GovData reference.

10 The surfaces

Six surfaces, three languages, one model.

The four scenarios above arrive on different surfaces — the trading desk on pgwire, the compliance team through GraphQL, the fraud investigator on Bolt, the lending team through SQL over HTTP — but they read the same model under the same enforcement. The surfaces are a convenience; the governance is not.

01

PostgreSQL wire

psql, JDBC, every PostgreSQL driver. The trading desk and the credit-risk team speak Provisa as if it were Postgres on port 5439.
02

GraphQL over HTTP

The canonical surface the others are generated from. Compliance queries, the admin UI and application backends read the model as a typed graph of fields.
03

SQL over HTTP

The same compiled statements as pgwire, posted as HTTP for clients that would rather not keep an open PostgreSQL connection.
04

Cypher on HTTP and Bolt

Neo4j-compatible on Bolt, so the fraud team's Browser speaks to Provisa unchanged, and HTTP for scripted Cypher where that is simpler.
05

Arrow Flight

Columnar results over Flight for the risk and analytics clients that would rather receive Arrow than serialise a result set twice.
06

MCP for agents

Agents connect through MCP and run under the caller's role. An agent can never do more than that person could — the masks and row rules travel.
THREE LANGUAGES SQL, GraphQL and Cypher are generated from the one model. Six surfaces to speak those three. Not six languages — three.
