Migrating

Your v2 metadata is a file. Provisa reads it.

Point the converter at the directory hasura metadata export gave you and it writes a Provisa configuration — permissions, relationships, actions and cron triggers among them, and the rest of the export named row by row in the table below.

One thing it does not read: a row filter that traverses a relationship. That is the most common permission shape in a multi-tenant v2 app, it is not converted, and until the converter is fixed it does not warn. This is a migration with a review step in the middle, and this page would rather say so than find out with you — start at what does not convert if you would rather read that first.

01 Two routes

Run it

Export your metadata the way you already do:

hasura metadata export

That writes the metadata/ directory — a databases/ tree with one file per table and an !include index, plus actions.yaml, cron_triggers.yaml, api_limits.yaml, inherited_roles.yaml and the rest beside it. It is the directory the next tab converts.

python -m provisa.hasura_v2 ./metadata -o config.yaml

The converter reads a metadata directory — the layout hasura metadata export produces, including its !include index, or the flat tables.yaml / actions.yaml layout. Omit -o and it writes to stdout.

The converter's five flags and what each one does
Flag What it does
-o, --output Output YAML path. Default stdout
--source-overrides Per-source connection overrides: host, port, credentials
--domain-map SCHEMA=DOMAIN pairs. Anything unmapped keeps its name
--auth-env-file A .env file. Converts JWT and JWK config, the admin secret and the claims map
--dry-run Parse and validate, write nothing
02 If you drive Hasura over HTTP

The metadata API returns one consolidated document rather than a directory:

curl -X POST http://localhost:8080/v1/metadata \
  -H "X-Hasura-Admin-Secret: <secret>" \
  -d '{"type":"export_metadata","args":{}}' > metadata.json

That document is an upload, not a command-line argument — the CLI above takes a directory. Take it to Admin → Import Hasura Config, which reads a consolidated .json, .yaml or .yml document as well as a .zip of an export directory, and runs the same parser and mapper the CLI runs.

IMPORT TAB No shell, no config round-trip: Admin → Import Hasura Config runs the same converters either way. Upload the document or a zipped v2 metadata directory, map schemas to domains, and the server returns the counts, the converter’s warnings and the generated configuration — editable in place, with nothing written until you press apply. An import is always a merge into what the organization already has.
03 Coverage

What converts

What a Hasura v2 export converts to, across eighteen kinds of metadata object
In your v2 export What you get
Sources A Provisa source per database. Connection details come from --source-overrides or the import tab, since the export names databases by environment variable
Tracked tables A table with publish: true
custom_name and custom_root_fields A table alias — select, then select_by_pk, then custom_name
Custom column names Column aliases
Object relationships A many-to-one relationship. One declared by foreign-key column alone names no target in the export; the converter resolves it through the inverse array relationship
Array relationships A one-to-many relationship
Select permissions, columns Per-role column visibility
Select permissions, row filters A row-security rule — for predicates on the table’s own columns, and for _exists. Not for a filter that traverses a relationship.
Insert and update permissions Writable columns per role
Delete permissions A write capability on the role
Inherited roles Converted
Computed fields A functions[] entry with kind: query
Tracked functions A functions[] entry, declared returns: void and visible to org_admin until you finish it
Actions with an HTTP handler A webhooks[] mutation. A non-HTTP handler becomes a functions[] placeholder with a warning to review it
Cron triggers A scheduler entry, with the cron expression and the enabled flag
api_limits A per-role rate, query-complexity and query-time limit. Complexity comes from node_limit; depth_limit has no counterpart and is dropped by design
Remote schemas A graphql_remote source, plus one landed table per Query root field your role SDLs expose. A non-null root argument becomes a native-filter column. A remote schema with no permissions lands nothing, because the export carries no other statement of its shape
A session variable in a filter X-Hasura-User-Id becomes current_setting('provisa.user_id'), bound from the identity’s user id and claims at query time
AT PREVIEW A v2 export names columns but carries no types, and a tracked table with no permission names no columns. The preview fills both in: it reads each reachable source’s information_schema.columns, types every untyped column, and lands every column of a table v2 exposed to nobody but its admin — visible to org_admin alone, because that is who could see it in v2. A source the preview cannot reach is reported, and its columns stay untyped for you to finish before apply.
04 The upside

What you get that v2 did not have

01

SQL and Cypher, not only GraphQL

The same model answers GraphQL, SQL and Cypher, with domain membership native to each. Your v2 permissions become the governance on all three rather than on the GraphQL endpoint alone.
02

Policy compiled into the statement

Five governance layers compile into one query plan before execution, at one place every surface goes through, plus an approval hook that runs before the plan and is not one of them.
03

API limits are in the configuration

api_limits becomes a per-role limit in the configuration rather than a setting on one deployment. Query complexity and query time convert exactly. The rate does not: v2 counts requests per minute and Provisa counts them per second, so re-read the rate on every throttled role — the arithmetic is in §5.
04

Sources beyond Postgres

72 source types. On a Trino engine, 63 are reachable and 37 are read live with no copy.

05 The gap list

What does not convert

NOT CONVERTED Row filters that traverse a relationship are not converted, and the converter does not tell you. A v2 filter like {"members": {"user_id": {"_eq": "X-Hasura-User-Id"}}} reads members as a column and user_id as an operator on it. There are three outcomes and none of them is an error:
What a v2 row filter converts to, and what each outcome means for the role
What you wrote in v2 What the converter produces What that means
{"user_id": {"_eq": "X-Hasura-User-Id"}} user_id = current_setting('provisa.user_id') Correct
{"members": {"user_id": {"_eq": "X-Hasura-User-Id"}}} members /* unsupported op: user_id */ A rule exists on the role and restricts nothing
{"_and": [{"project": {"id": {"_eq": …}}}, {"deleted": {"_eq": false}}]} (project /* unsupported op: id */ AND deleted = FALSE) Narrower or broader than the original, with no indication which
An operator the converter does not know TRUE, which is then discarded The role imports with no row restriction at all

So: review every role’s row rules against your v2 permissions before the deployment serves traffic. The rules that need rewriting by hand are the ones that reach through a relationship. An _exists subquery converts correctly and is the shape to rewrite them into — a v2 _exists on public.project comes out as EXISTS (SELECT 1 FROM public.project WHERE owner_id = current_setting('provisa.user_id')).

Reported and not converted

Five sections of the export have no target in a Provisa configuration. Two of the five are load-bearing and worth planning for before you convert.

The five export sections that are reported and not converted, with the file each one is in
Section The file in a CLI export Why it matters
allowlist allow_list.yaml If you ran v2 with an allowlist you were running it as a security control. It does not come across
rest_endpoints rest_endpoints.yaml Usually in production clients’ URLs. They do not come across
query_collections query_collections.yaml The collections an allowlist refers to
network network.yaml Not converted
opentelemetry opentelemetry.yaml Not converted

The warnings arrive under an Import warnings (n): heading at the end of the run. Converting a directory export with a populated allowlist in it contributes this line, which names the section, the file it was found in, and what was done with it:

  [allowlist] [allow_list.yaml] allowlist is present in the export and is not converted

The section is named by its metadata-API key and the file by its name on disk, which for the allowlist are one underscore apart — allowlist against allow_list.yaml. It is the only row here where the two differ, and the warning prints both so you never have to guess which to search for. From a consolidated document there is no file to name, so the line is the same without the bracket. Warnings go to stderr, so they are still on your terminal when the configuration goes to a file.

Converted, with something to check

A wildcard column permission imports as a single placeholder column named *, which is not expanded to the table’s real columns and is not read as “all columns” anywhere — so the role that had every column arrives able to see none of them, and you list the columns it should see. On the import tab the preview names it — <source>: <schema>.<table>.* is not a column of the source table; it stays untyped — and from the command line it is not warned about at all; the untyped column is refused when you apply. Either way it cannot reach production silently.

Converted to per-table event-trigger config — operations, webhook URL, retry policy — with a warning that fidelity is limited. Verify each one rather than assuming it or rewriting it.

The export names no target table, so the converter resolves it through the inverse array relationship. Where there is no inverse the relationship is dropped, with a warning telling you to declare it with manual_configuration or add it after import.

Not supported. Configure an explicit provider — firebase, keycloak, oauth or simple — and the converter warns if your .env carries the webhook setting. A CLAIMS_MAP that is not valid JSON is also warned rather than guessed at.

Every tracked function converts to a functions[] entry, but the converter cannot read the function body: each one lands declared as returning void and visible to org_admin alone. Set the return type and the roles on each function you want exposed — the entry is a stub with the right name, not a finished definition.

v2 sets requests per minute and Provisa sets requests per second, so the import divides by 60 and rounds, with a floor of one. A role throttled to 10 requests a minute arrives serving 60; one set to 150 a minute arrives held to 120. The value is exact at a multiple of 60 and rounded otherwise, in either direction, with no warning. Query complexity and query time convert exactly. Re-read the rate on every role you throttled on purpose.

06 Before you apply

Preview before you apply

The converter’s warnings are the most useful thing it produces. Run it twice: once to read them, once to keep the output.

python -m provisa.hasura_v2 ./metadata --dry-run

--dry-run parses, converts and validates the result against the configuration model, prints Dry run: validation passed. and then the warning summary, and writes nothing. Both go to stderr.

The two surfaces do not print the same warnings, and it is worth knowing which you are reading. The command line reports what the parser and mapper found in your export: dropped relationships, placeholder handlers, unconverted sections, the name collision in §5. The import tab reports those and then one more pass — it reads each source’s real columns, so the unreachable-source, untyped-column and columns: "*" warnings exist only there.

SIZING THE REVIEW The summary counts them — Import warnings (3): and a category on every line — so the output tells you how big the review is before you commit to it. Two things to check in it every time, because neither is an error and both change who can see what: a [relationships] warning, which means a relationship was dropped, and every role’s row rules, against the v2 permissions they came from.
07 Conceded

When Provisa is not the answer

01

You want a managed service

Provisa does not offer one. It is self-hosted: your infrastructure, your cloud, or air-gapped — which is the only configuration some regulated buyers can accept, and no help at all if zero operations is your requirement. If it is, this is a disadvantage and there is no version of it that is not.
02

You need your v2 app to keep working unchanged

The import produces a Provisa configuration, not a Hasura-compatible endpoint. Your GraphQL schema is regenerated from the model, so client queries are checked against the new schema rather than guaranteed by it, and the row rules in §5 need review before anything serves traffic.
08 Hasura’s own words

v2 and DDN, in Hasura’s own words

DATELINE Read from Hasura’s published documentation on 14 October 2026.

Hasura’s upgrade guide states: “Currently, there is no in-place upgrade path from Hasura v2 to Hasura DDN.” The three strategies it documents — GraphQL-based routing, URL-based routing, and parallel deployment with phased deprecation — all run v2 and DDN side by side while features move across by hand.

Hasura’s own v2-to-DDN API parity table lists Cron Trigger as ❌, and Event Trigger and API Limits as WIP. Those are three of the things the converter on this page reads out of your v2 metadata — §3 above.

STILL SUPPORTED Hasura also states that “Hasura v2 is still supported and will be maintained according to our LTS policy”, and their version-support policy lists v2.45 as Active LTS supported through December 2027 and v2.50 as Active LTS planned through December 2028. This page makes no argument that you have to move. It argues only that if you do, your v2 metadata is a file either way.
