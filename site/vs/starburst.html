Compare

If you run Starburst, keep it.

Starburst Enterprise and Galaxy are Trino: a mature MPP SQL engine with a cost-based optimizer, a deep analytics connector ecosystem for lake workloads, and the operational record to match. Provisa is not a replacement for that. It is a governed semantic layer — one model, three query languages, policy compiled into the statement — that runs on a Trino-protocol coordinator as a trino-byo engine, including one you already operate.

THE QUESTION The question is rarely “Starburst or Provisa”. It is whether you need a governed model and three query languages above the engine you already have.
01 Conceded

Four places Starburst is better. We are not going to argue any of them.

01

Query acceleration, as a category

Starburst has a mature cost-based optimizer with a statistics pipeline behind it, and its documentation for 482-e.3 LTS and Galaxy describes an entire acceleration layer beyond it: Warp Speed’s automatic smart indexing built from observed query characteristics, Cached Views — auto-refreshing materialized views with table scan redirection, managed by a cache service — and Galaxy materialized views over any object-storage catalog. We have no counterpart to that layer. Provisa has no CBO at all. What it has instead is narrower and differently sourced: hot lookup tables pre-materialized into the query, automatic materialized-view rewrite, and relationship-driven join materialization. Our argument is not that we are faster. It is that our optimizations fall out of governance artifacts someone had to approve anyway, so the acceleration arrives without a second configuration surface to own.
02

Raw query scale

Starburst exceeds Provisa on raw query scale. For petabyte-scale ad-hoc analytics over a lake, it is the better tool — and it is a tool Provisa can run on.
03

Managed service

Galaxy is a real managed service. Provisa does not offer one: it is self-hosted and on-premises. If zero ops is a requirement, that is a real disadvantage and it is ours.
04

Track record

Starburst has customers in production at scale with public references. This is Provisa’s first release and we have no public reference customers yet. You should weight that.
02 Not a difference

Two things we both do, and neither of us wins.

OVERLAP Both federate across sources. Both push predicates down into the source rather than dragging rows back to filter them. If a comparison matrix somewhere scores either of those as a Provisa advantage, it is wrong.

04 The procurement difference

Four differences that decide an audit.

01
Where the enforcement point sits Starburst’s is an engine access-control plugin, so it serves SQL. Provisa’s is compiled into the statement before the engine sees it, so one policy object serves SQL, GraphQL and Cypher. That is the uniformity claim that is actually ours: three languages, one policy — not coverage across their connectors, which their documentation does not limit and we have not tested.
02
Where the gap is, and it is a documented one Their rules filter SHOW commands — that part works. Their own documentation states those rules do not apply to system-defined tables in information_schema, and neither do filter and mask rules. So the control has a second path through it, and the second path is the one a tool takes. Provisa generates information_schema per role, which is why there is no second path. Narrower than “no per-role schema”, true, and it still wins the audit argument.
03
Joins are policy Their documentation for 482-e.3 LTS and Galaxy describes no equivalent of a join guard — no approval-gated relationship catalog a join must match. In Provisa every join in SQL and Cypher must match a relationship someone approved. The guard is governance policy rather than a hard boundary and it has documented bypasses, which is why the claim is made at the setting that closes them: in high-security mode it is not bypassable, by anyone, including a role granted the bypass by mistake.
04
The access record is a table Append-only, with UPDATE and DELETE refused by the database itself on a PostgreSQL control plane, query text never stored in the clear, and exposed as a queryable table in the ops domain rather than a log file.

05 Who consumes it

Analytics consumers, and the other kind.

Starburst serves SQL and JDBC consumers, with Arrow Flight through Trino. That is the right shape for an analytics estate. If the things that need your data include an application, a service or an agent, the shape is different.

Said precisely, because the sloppy version of this is checkable in ten seconds: Starburst has an HTTP interface — the Trino client protocol is HTTP and JSON, and their own concepts page says coordinators communicate with clients using a REST API. It is a statement-submission and polling API for SQL clients. It is not a resource API.

06 Getting one running

Against a cluster, or against a laptop.

Starburst Enterprise deploys two documented ways — Helm, and Starburst Admin, a set of Ansible playbooks that is the supported path for bare-metal servers and virtual machines. They also publish a Docker try-it path. So the shape difference is not that they cannot run outside Kubernetes; it is what the artifact is.

Provisa’s claim is one artifact across every shape: laptop, single VM, HA VM cluster with no orchestrator, Kubernetes — same product, same config, same governance, no separate pricing tier for the on-prem form, and pip install as the floor. Their on-prem path is a separate platform with a separate pricing tier and an Ansible control node. Ours is the same wheel the developer already ran.

The floor
# Python 3.12 — 3.13 is not supported.
# Not Linux aarch64: no pgserver wheel, so the embedded tier does not run there.
pip install "provisa[embedded]"
provisa run
EMBEDDED TIER The embedded tier runs on DuckDB. No JVM means no Trino — it is the whole control plane and UI on one engine, not multi-engine federation in a wheel. Point it at an engine you run for that.
07 Honest advice

Three situations. One of them is not us.

Buy Starburst

  • Your problem is ad-hoc analytical SQL over a large lake, your consumers are SQL consumers, and you want it managed — or you want an acceleration layer we do not have.
  • Galaxy is a good product and this is what it is for.

Buy Provisa

  • Your consumers are not all SQL.
  • You need the same row filters and masks on a MongoDB collection, a Salesforce object and a Postgres table.
  • You need to answer a reviewer about what a role can reach, not what it is allowed to request.

Run both

  • You have a Trino-protocol coordinator and it works.
  • Point Provisa’s trino-byo engine at it and you keep the engine and gain the model.
