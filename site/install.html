Provisa / Install
Install

One wheel. Everything inside.

# Python 3.12 required — 3.13 is not supported.
# Not Linux aarch64: no pgserver wheel and no source distribution,
# so the embedded tier does not run there. Use the container tier.
python3 -m venv .venv && source .venv/bin/activate
pip install "provisa[embedded]"

provisa run --demo   # the bundled sample domains, on embedded SQLite

Current release 0.1.0a479. This is a first release and we say so. Run on 2026-10-14 on CPython 3.12.15 in a fresh virtualenv; the API and the UI both answered 200 and the server printed ✓ Provisa is ready.

That is the demo data. Pointing it at your own sources is the next step and it is a config file, not another install — §3, tab 2.

The embedded tier runs on DuckDB. No JVM means no Trino — this is the whole control plane and UI on one engine, not multi-engine federation in a wheel. For that, point it at an engine you run.

Download for macOS Download for Windows Download for Linux

The desktop installer is a single download driven by start, stop, status and open. By default it runs everything natively: DuckDB as the federation engine, an embedded PostgreSQL control plane, an in-memory cache. Trino on Docker or an external engine are opt-in choices in the setup wizard, and Docker or a VM is provisioned only if you pick one of them. The run command waits for the API to report ready before it prints success, so a green line means a green line.

01 What is running

Three processes and no cluster.

The engine

DuckDB, in process. It is the only engine in the wheel — omitting the JVM omits Trino. Good for a desktop, an edge box and development; not for multi-user production, and we would rather tell you that here than have you find out in staging.

The control plane

An embedded store holding the model, the operating state and the platform state — pluggable, chosen by a SQLAlchemy URI, and PostgreSQL everywhere that is not a desktop. One consequence worth knowing before you build a control narrative on it: audit-log immutability is enforced by PostgreSQL rules, so on the desktop tier append-only is an application convention rather than a database guarantee.

The cache

In memory on the desktop. Redis where one is configured.
NO CALLS Nothing phoned home. The whole distribution installs with no network calls at install time or first launch, and the add-ons are found locally, then on mounted volumes, before anything is downloaded.
02 First queries

Register a source. Register a table. Ask three ways.

Registering a source exposes nothing. A table is queryable only after someone registers it; an unregistered table is invisible, absent from the schema browser and unnameable in a query. That is the default, not a setting.

provisa run --demo
# Loads the bundled pet-store and shelter sample domains over embedded
# SQLite, and marks the session as a demo run. No Docker. The UI opens
# at the URL it prints.
# provisa.yaml — a source, a domain, and one table with its columns.
sources:
  - id: sales-pg
    type: postgresql
    host: localhost
    port: 5432
    database: sales
    username: provisa
    password: ${env:PG_PASSWORD}

domains:
  - id: sales

tables:
  - source_id: sales-pg
    domain_id: sales
    schema: public
    table: orders
    columns:
      - name: id
        data_type: integer
        visible_to: [analyst, org_admin]
      - name: customer_id
        data_type: integer
        visible_to: [analyst, org_admin]
      - name: total
        data_type: decimal(10,2)
        visible_to: [analyst, org_admin]
      - name: margin
        data_type: decimal(10,2)
        visible_to: [org_admin]

roles:
  - id: analyst
    capabilities:
      - query_development
    domain_access:
      - sales
PROVISA_CONFIG=provisa.yaml provisa run

There is no publish-the-whole-table shorthand. A column you do not list is not published, and margin above is listed for org_admin only, so an analyst session cannot name it. That is the mechanism behind the sentence above this section: registering a source exposes nothing, and a table is queryable only after someone says which columns of it are.

This is one table. The configuration we ship with the installer has the same shape — config/provisa-install-base.yaml enumerates every column of the table it publishes with its type and its role list, and price on the demo's pets table is visible to org_admin alone, exactly as margin is here. roles: is a required key, so the file carries one. The analyst entry above is what scopes that role to sales; the product seeds analyst and org_admin itself, and a config that tries to redefine org_admin is refused by name. On a provisa run against revision 5's block (no roles:) the server exited at startup on roles — Field required; with the block above /ready answers in under ten seconds, and over pgwire -U analyst is refused margin with [V003] while -U org_admin sees all four columns ([PRO-53], 16 Oct 2026).

# The Postgres listener is off until you give it a port.
# 5439 is what our Helm chart and installer set; any free port works.
PROVISA_PGWIRE_PORT=5439 provisa run --demo

# In another shell — psql speaks to Provisa as if it were Postgres
psql -h 127.0.0.1 -p 5439 -U analyst
SELECT p.name, p.species, v.visit_date, v.reason
FROM pet_store.pets p
JOIN pet_store.pet_visits v ON v.pet_id = p.id
LIMIT 5;

Run on 2026-10-14. What comes back:

  name  | species | visit_date |         reason
--------+---------+------------+-------------------------
 Cat 1  | cat     | 2025-02-14 | Annual vaccination
 Cat 2  | cat     | 2025-03-02 | Dental scaling referral
 Dog 1  | dog     | 2025-04-08 | Limp in left forepaw
 Lion 1 | lion    | 2025-01-27 | Weight check
(5 rows)

Three corrections in that block, each of which would have cost a reader their first five minutes. Revision 3 had psql -h localhost -p 5439 -U admin and no --demo. -h localhost resolves ::1 first against an IPv4-only listener, so the reader sees a red connection refused before it falls through and works — 127.0.0.1 is not a style preference on this page. The demo has exactly one role, analyst; there is no admin, and -U admin returns ERROR: No schema for role 'admin'. And the tables the query names exist only under --demo.

NO PASSWORD That psql command has no password in it, and it does not need one. The bundled demo starts with auth: provider: none, which puts pgwire in trust mode: the username is taken directly as the role and the secret is ignored. The listener also binds every interface. On a laptop that is the right default and it is why the command above is two words long. It is not a configuration to put on a network — our own documentation says not to use trust mode over an unencrypted connection, and we would rather you read that here than discover it.

Set auth.provider: basic with auth.scram: true and pgwire advertises SASL with SCRAM-SHA-256, so the password is proved rather than sent. With TLS on the listener and a client CA configured, the client certificate is verified in the handshake before any credential is examined.

03 The proof

Now ask for something you have not approved.

The same psql session, one join away from the one that worked — two tables in different domains with no approved relationship between them:

ERROR:  [V002] Invalid JOIN: employees.id = pets.id
        — no approved relationship exists between these tables on these columns

That is the governance pipeline refusing an unauthorised join at the Postgres wire, to a stock psql client, with a diagnostic naming the two columns so a data engineer can act on it rather than guess. Nothing about the refusal is specific to our own tooling: the client is the one already installed on the reader's machine.

NOT A WALL A joinable-looking pair of columns in two systems is the ordinary way a wrong number reaches a dashboard, and most engines in this category would return the cartesian product without comment. The approved-join guard is governance policy rather than a hard boundary — two bypasses exist and they are named on /why/governance — but in high-security mode it is not bypassable by anyone.

There was no password on that session. Tab 3 connects in trust mode, so the role was asserted by the client and taken at face value — and the join was refused anyway. Authentication decides who you say you are; the compiled plan decides what that role may do, and the second does not depend on the first being strong. That is not a licence to leave the first weak — in trust mode anyone can assert any role, which is why the callout in tab 3 says what it says. It is proof that the wire is not a bypass. Most readers conflate the two, and this is the one place on the site where they come apart with evidence in front of them.

04 Shapes

The same product, from a laptop to an air-gapped rack.

Each deployment shape, how it is installed, and what runs in it
How What you run
Laptop The installer, or pip install "provisa[embedded]" on Python 3.12, and not on Linux aarch64 Everything natively. No Docker.
Linux box AppImage Bundles the core and observability container images and stages compose files out to a writable location — so unlike the row above, this path uses Docker. A non-interactive first launch installs a systemd unit so Provisa starts on boot.
One VM, one team Docker Compose One command brings up the server, the engine and the connectors. The demo upstreams and the telemetry stack are separate compose projects, so they start and stop on their own.
Kubernetes Helm Scales engine workers and validates its own values. Authentication is chosen at install time and does not require Firebase.
Cloud VM Terraform, GCP / AWS / Azure Provisions the stack, stages the release artifacts, runs it under systemd. AWS builds a multi-node cluster behind load balancers, and the interview lets you switch pgwire, Bolt, MCP and gRPC on or off.
Air-gapped Any of the above No network calls at install time or first launch. The Python version is pinned, so a mirror knows which wheels to hold. Local embedding models via Ollama or HuggingFace.
CLUSTER In a cluster deployment, every endpoint is served over TLS — UI and API as well as pgwire, Bolt and Flight — and Provisa generates self-signed certificates when none are supplied. The Helm chart takes an existing certificate secret or a cert-manager issuer.
05 Your engine

You already have the engine. Point at it.

# Federate on a Trino coordinator you already run
TRINO_HOST=trino.internal TRINO_PORT=8080 provisa run

If your coordinator is behind a URL rather than a host and port, PROVISA_ENGINE_URL is the documented alternative.

# Or federate in your own PostgreSQL. The extensions it federates
# through have to be installed in that server.
pip install provisa-pg-ext
provisa pg-ext install --docker my-postgres
docker restart my-postgres          # pg_duckdb loads only at server start
provisa pg-ext install --docker my-postgres --create

The pg-ext bundles are built for PostgreSQL 16 only, on linux-x64 and darwin-arm64. A managed service without filesystem access — RDS, Cloud SQL — cannot take them; use the extensions the service offers.

06 Licence

Two different things are called a licence. Here are both.

Provisa is source-available under Business Source License 1.1. Production use is free for an organization that, with its affiliates, has fewer than 100 employees and contractors and under USD 1,000,000 in annual revenue, budget or expenditure, with 90 days' grace if you cross either threshold. Any other production use needs a commercial licence. Each released version becomes GNU General Public License, Version 2.0 or later on the fourth anniversary of that version's first public availability. Non-production use, evaluation included, is free at any size, forever.

Separately, and confusingly similarly named, there is a file. An Unregistered marker appears in the footer from first launch, whenever the deployment is not licensed — it is not an expiry event. Provisa runs for a 30-day trial without a licence; past 30 days an unlicensed deployment also shows a banner in the UI and a notice on each protocol's own channel. Nothing stops working: no feature gate, no row limit, no read-only mode, no expiry.

That notice travels on each protocol's own non-fatal channel — pgwire NoticeResponse, Bolt success metadata, Flight app_metadata, gRPC trailing metadata, a REST header — and it never modifies the result body, the row stream, or any schema-typed field. A licence reminder that cannot corrupt a result set is a design decision, and it cannot even fail the request it rides on.

That file is free. You get it by registering on a web form and clicking the confirmation link; the signed file arrives after that. It proves its own validity offline, with Ed25519, and is tied to the machine it was issued for, so an air-gapped install is licensed like any other. The licence is requested by you, from a browser — not by the install, which makes no network calls at all — and applying it starts no telemetry either.

NOT THE SAME The free licence file is a registration artifact. It is not the BSL production grant. If your organization is over either threshold, you need a commercial licence to run Provisa in production — and the free file does not change that.
