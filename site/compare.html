What Provisa is, in terms of things you already run.

Provisa is a governed semantic layer. Federation, metrics, ontology and governance come from one model, and the engine underneath it is yours and swappable.

It is not an MPP query engine, not a graph database and not a GraphQL gateway. If you run one of those, it stays — the comparison on this page is about what sits above it, and in two cases Provisa runs on the thing you already operate.

Four categories, four questions

The four categories of product Provisa is compared with, and what Provisa does with each.
Category The question it answers What Provisa does with it
MPP SQL engine — Trino, Starburst How fast can I scan this lake Runs on it. A Trino-protocol coordinator, including one you already operate, executes the federated half of a plan
Graph database — Neo4j What does this traversal tell me Leaves it alone. Cypher over your relational and API sources is a different job from a native graph store, and deep traversal is the store's
GraphQL gateway — Apollo GraphOS, Hasura How do my teams' services become one API Answers GraphQL from the same model that answers SQL and Cypher, with the permissions in the model rather than in the gateway
Data virtualization — Denodo and the category around it How do I query what I cannot move The same question Provisa answers, with the governance compiled into the statement rather than applied around it
THE ROW THAT DECIDES The row that decides it is usually the second column. If your question is how fast can I scan this lake, the answer is an engine and Provisa is not one. If your question is who is allowed to see what, across all of it, and can I prove it — that is the model, and the engine is an implementation detail of the answer.

Two comparisons in detail

Starburst and Trino

  • Starburst Enterprise and Galaxy are Trino: a mature MPP engine with a cost-based optimizer and a deep analytics connector ecosystem.
  • If you run it, keep it — Provisa runs on a Trino-protocol coordinator, and the comparison that matters is between an engine with access control and a model with an engine underneath it.

If you run Neo4j

THEIRS Cypher is theirs and graph analytics is theirs. Graph Data Science 2026.09 documents centrality, community detection, similarity, path finding, node embeddings and topological link prediction. If what you need is deep traversal or GDS, the answer is Neo4j and this page is not going to argue with you.

Where the two stop overlapping is scope and enforcement. Read from Neo4j's published documentation on 14 October 2026 — Neo4j 2026.09 (Operations Manual), Cypher 25, Graph Data Science 2026.09, the Neo4j GraphQL Library v7 and the Neo4j JDBC Driver manual.

What Neo4j's documentation describes on 14 October 2026, and what Provisa does, row by row.
What their documentation describes What Provisa does
Composite databases query across Neo4j databases — local or on remote DBMSs — through a single Cypher query, and every constituent is a Neo4j database. LOAD CSV reads files, including from S3, as import that parses a row at a time into CREATE/MERGE, so the file does not become a queryable table. No REST, GraphQL or gRPC service is a governed source. 72 source types in one model. On a Trino engine, 63 are reachable and 37 are read live with no copy — relational, NoSQL, object storage, streams and HTTP APIs as governed, joinable tables.
Access control hides; it does not transform. Read and traverse privileges on labels, relationship types and properties, with predicate conditions on property values. Their documentation describes no mechanism for returning a transformed value. Column masking is a transformation: a value comes back redacted, truncated or substituted rather than withheld, and which one is a policy on the column.
DENY fails open, in their words: "a DENY rule fails open when its criteria cannot be evaluated, which means the restriction is not applied". Governance is compiled into the query plan before execution, at the one place every surface goes through — SQL, GraphQL, Cypher and every wire protocol alike. A rule that cannot be evaluated is a plan that does not run.
Vector embeddings live in the graph. Cypher 25 vector indexes are supported, not beta, cosine and Euclidean, over node and relationship properties. An external vector has to be imported first. Embeddings are declared on a source, including one with no native vector support, and governed like any other column.
Their catalog is per-role for labels, not for property keys. db.labels() and db.relationshipTypes() are documented as returning results "according to the user's access rights"; db.propertyKeys() is documented as listing "all property keys in the database", with no such caveat. Every catalog surface resolves per role from the same model the query resolves from.
WHAT THIS PAGE DOES NOT CLAIM Nobody has run this, so there is no claim here about the behaviour — only about the documentation. The asymmetry above is what Neo4j's own documentation says, and it is all this page asserts. We are not claiming that Neo4j property names leak to a role that cannot read them. They may not; we have not tested it, and a comparison page is not the place to find out in public.

If you run Apollo GraphOS

THEIRS Composing GraphQL services your teams already built is theirs. And it is more than it was: Apollo Connectors register an HTTP/JSON API declaratively with @connect and @source, so a REST API no longer needs a subgraph service either. If your problem is a federated graph over services and HTTP APIs your teams own, GraphOS is built for exactly that.

Read from Apollo's published documentation on 14 October 2026 — GraphOS Router v2, Federation v2.12, and the Connectors connect spec v0.4. GraphOS is continuously released, so it carries a read date rather than a version.

What Apollo's documentation describes on 14 October 2026, and what Provisa does, row by row.
What their documentation describes What Provisa does
The transport is the boundary, in their sentence: @connect "can only retrieve data from HTTP APIs that return JSON data and, optionally, accept a JSON body". No database, object store, file, stream or gRPC service is a connector target. A database, an object store, a file, a stream and an HTTP API are all sources of the same kind, and a join across two of them is one statement.
Authorization is field-and-type. @authenticated, @requiresScopes and @policy are enforced at the router and filter unauthorized fields and types before execution. Their documentation describes no row or record predicate and no value transformation. Row-level security and column masking are layers of the plan, so the predicate is in the statement that reaches the source rather than a filter around its result.
Schema differentiation is per variant. Contracts filter individual fields by @tag and publish a separate variant with its own router, so a new audience is a new variant to compose and operate. The schema is generated per role from one model at request time. A new audience is a role, not a deployment.
The air-gapped thing is the router, not GraphOS. Offline licences exist — Enterprise, on request, valid for the contract term or one year, 28-day grace, re-fetched and redistributed every renewal, supergraph schema read from a local file. The registry, composition, contracts and observability stay SaaS. Self-hosted end to end, with no vendor service in the deploy path and no phone-home.
TWO THINGS THIS PAGE NO LONGER CLAIMS Two things that used to be on this page and are not claims any more. The GraphOS Router separates entity-cache entries by authorization context and supports a per-user private_id, so security-partitioned caching is not a differentiator. And natural-language query is documented by both Neo4j and Apollo, so neither is the differentiator either — what is ours is the boundary around it: the model is handed the caller's per-role schema, so a table or column the role cannot see is not in the prompt, and the generated statement goes through the same compiler validation as a hand-written one. The failure mode is absence rather than refusal — the model cannot propose a table the caller may not see, because it was never shown one.

How this page is made

Every negative statement above is a claim about a named product's published documentation on a stated date. That is a deliberate constraint and it cost us rows.

01

A date, or it does not ship

A comparison claim carries the product, the version where there is one, and the date the documentation was read. Where a vendor releases continuously, it carries the date alone. A column nobody has re-read publishes nothing.
02

Their nearest capability, before our distinction

A row names what the other product does document before it draws a line. Rows that could not do that were removed rather than softened.
03

No bare negatives

"Not available" and "no X" are treated as defects rather than claims. We published two of them about natural-language query and both were wrong.

The file these rows come from is in the repository, with the read dates in it, per cell: docs/competitive_analysis.md. When a cell has no date on it, this page has nothing to say about it.

Where Provisa is the wrong answer

01

You want a managed service

Provisa does not offer one. It is self-hosted: your infrastructure, your cloud, or air-gapped — which is the only configuration some regulated buyers can accept, and no help at all if zero operations is your requirement.
02

You need the fastest scan over a lake

That is an MPP engine's job, and a mature one will out-run Provisa on raw analytical scale. Point Provisa at it.
03

Your problem is a graph

Deep traversal and graph algorithms belong in a graph store. Cypher over relational and API sources answers a different question from the one GDS answers.

Bring us the comparison you are actually running

If the product you are comparing is not on this page, the fastest route is a conversation — the four categories in §2 cover most of what gets compared to Provisa, and the answer usually turns on which of them your incumbent sits in.
