The governed data layer

Federation, metrics, ontology and governance from one model. Nothing to keep in sync.

A catalog tells an agent what it should do. Provisa enforces what it can do.

Register a source, register the tables you want published, and ask once in English: the answer comes back on up to six governed surfaces — SQL, GraphQL, Cypher, gRPC, JSON:API and OpenAPI — each one generated for your role. Or write the query yourself in SQL, GraphQL or Cypher. Your policy is compiled into the statement before it runs — not checked around the result — and the data stays where it already is.

01 Governance

Five layers, rewritten into the statement. Not filters around the result.

Every request — GraphQL, Cypher, SQL, a protocol buffer — becomes one canonical governed statement before execution, at the single place every surface goes through. There is no query path that skips it. Five of the six below are compiled into the plan. The sixth runs before it.

00
Introspection filtering Objects outside a role are absent from the schema, the catalog and the browser. Not present and refused — absent.
01
Domain access A query touching a table outside the role's domain access is rejected at compiler validation, before execution.
02
Row-level security Per-table, per-role WHERE injected into every SELECT, evaluated against the raw data.
03
Column visibility and masking Invisible columns stripped and masked values replaced before results leave the server.
04
Predicate guard A masked column is refused in WHERE and HAVING at parse time — because otherwise a caller binary-searches the value they cannot see.
Before execution — approval hook An attribute-based callout over webhook, gRPC or a Unix socket can refuse the statement before it runs. Not part of the plan; a decision taken on it.

Public-column publishing — serving a published column to an unauthenticated reader — is designed and not built, so it is not a layer and is not counted here.

Every join in SQL and Cypher must match a relationship someone approved. In high-security mode that is not bypassable, by anyone — including a role granted the bypass by mistake.

02 One question

Ask once in English. Up to six governed surfaces answer.

One question is compiled to SQL, GraphQL, Cypher, gRPC, JSON:API and OpenAPI, each one generated for the asking role and run through the same compiled governance. Labels, fields and table names all come from the one model, so the answers agree by construction rather than by discipline.

-- Asked in English: "what has each customer spent?"
-- Orders in Postgres, customers in MongoDB. One governed statement,
-- then the dialect of whatever will run it.
SELECT o.customer_id, COUNT(*) AS count, SUM(o.total) AS sum_total
FROM orders o
GROUP BY o.customer_id;
# The schema is generated per role: you see your own tables and columns
{
  orders_group_by(by: [customer_id]) {
    groupKey
    aggregate { count sum { total } }
    nodes { customer { name } }
  }
}
// Labels come from the model. There is no graph to load.
MATCH (c:Customer)-[:PLACED]->(o:Order)
RETURN c.name, count(o) AS count, sum(o.total) AS sum_total
# The call a typed client would make, against the proto generated for
# your role — and the message that client would receive back.
QueryOrdersGroupBy(by=[customer_id], funcs=[count, sum],
                   include_nodes=true, include=[customer.name])

OrdersGroupByRow {
  group_key: {"customer_id": 4812}
  aggregate: { count: 9, sum: { total: 18422.50 } }
  nodes:     [{ name: "Northwind Traders" }]
}
# The deep link is the question. ?include= carries the relationship
# projection column by column, so nothing extra comes back.
GET /data/jsonapi/sales/orders
    ?groupBy=customer_id&aggregate=count,sum
    &includeNodes=true&include=customer.name
# The same question on the REST surface, whose own ?includeNodes= takes
# the dot-paths directly. Swagger UI serves the spec for your role.
GET /data/rest/sales/orders
    ?groupBy=customer_id&aggregate=count,sum
    &includeNodes=customer.name
gRPC, JSON:API and OpenAPI are the request a client of those protocols would send and the envelope it would receive, computed through the governed pipeline — not a round trip over a socket. Those three express row, aggregate and group-by questions; anything else comes back marked not applicable on that surface, which is what the product shows on screen. An arbitrary question — a join across Postgres, MongoDB and Elasticsearch, say — is carried by SQL, GraphQL and Cypher.

Relationships in Cypher are joins between tables, which is why they carry no stored properties.

03 Interfaces

Seven listeners. Sixteen surfaces. None of them a new client library.

Seven is the number that is not a taxonomy: seven server listeners, each binding its own port. HTTP, gRPC and Arrow Flight start by default; pgwire, Bolt, Airport and MCP are off until you give them a port. Fifteen client-facing surfaces ride those seven. The sixteenth goes the other way — a governed change stream out to a Kafka topic. These sixteen are ways in; the six governed surfaces above are what one English question comes back on. Different count, different thing.

The seven server listeners, which start by default, and the client-facing surfaces each one carries
Listener Default Carries
HTTP on GraphQL REST / JSON:API / OpenAPI SQL Cypher WebSocket SSE Python client
gRPC on A proto generated per role, showing only that role's tables and columns
Arrow Flight on Flight SQL ADBC JDBC — the JDBC driver moves results as Arrow over Flight
pgwire off until you set a port SQL only. psql, DBeaver, Tableau, Superset, anything with a Postgres driver
Bolt off until you set a port Cypher. Neo4j Browser, Bloom, cypher-shell and the official drivers; each of your roles appears as a database
Airport off until you set a port DuckDB attaches to Provisa as a catalog, on its own listener
MCP off until you set a port Governed tools for agents, over streamable HTTP at /mcp

And outbound, which is why the count is sixteen and not fifteen: a governed change stream to a Kafka topic, carrying the same row filters and masks as a read.

Governance is uniform across all of them — same compiled statement, same role. Command invocation is not: registered commands reach GraphQL, pgwire SQL and REST, and do not yet reach MCP, Flight, gRPC or Cypher.

04 Reach

72 source types
63 reachable
37 read live with no copy

Those three numbers are one command apart, and the third is the one that matters: a source read live is queried in place, not copied into a store first. Of the 72, 66 are data systems — the other six are two data-quality integrations, a profiler, and three public-content sources. We would rather you had that breakdown from us.

Live, with aggregates pushed down

PostgreSQL, MySQL, MariaDB, TiDB, CockroachDB, YugabyteDB, Greenplum, SingleStore, SQL Server, Oracle, Exasol, Snowflake, Databricks, BigQuery, Redshift, ClickHouse, Iceberg, Delta Lake, Hive.

Live, predicates only

MongoDB, Cassandra, Redis, Elasticsearch, Kafka, Prometheus, Salesforce, ServiceNow, SharePoint, Splunk, cloud inventory. Aggregates do not push down to these; the engine does them.

Read and replicated

Everything else — OpenAPI and remote GraphQL services, Neo4j, SPARQL, SQLite, Cosmos DB, Google Workspace and the rest. Provisa reads them and lands a copy the engine can query.
ClickHouse, MongoDB, Snowflake, Databricks and BigQuery are all read in place on a Trino engine. Predicates and aggregates push down into the source; joins execute above it.

And the scope argument, because it generalises: Provisa is the governed join across the inventories you already have. It does not scan, patch or replace any of them.

05 No lock-in

The data does not move, and the engine is yours.

Provisa compiles every request to one canonical PostgreSQL-style statement and then translates it into the dialect of wherever it runs. The engine that executes is configuration. What changes with it is not whether Provisa works — it is how much reaches live.

The three classes of federation engine, the keys in each, and what changes when you run on one
Class Keys What changes
Federating trino trino-byo pg duckdb clickhouse clickhouse-server Read sources in place. A cross-source join runs without landing its inputs first
Warehouse snowflake databricks bigquery fabric synapse Partial federators. The warehouse executes what it reaches natively and lands the rest into itself first
SQLAlchemy One generic runtime, pre-named for twenty databases No federation connectors. Everything lands in the target store and is federated with plain SQL

32 engine keys in total — six federating, five warehouse, and one generic SQLAlchemy runtime pre-named for twenty databases. Run on the Trino-protocol coordinator you already operate if you have one. Governance does not change with the engine, because it runs in the compiler rather than in the engine. What does change is how much reaches live, which is what the table above is for.

06 Deploy

A laptop, a VM, a cluster, or an air-gapped rack.

Laptop

One wheel with the UI inside it. DuckDB as the engine, an embedded PostgreSQL control plane, an in-memory cache. No Docker.

Single VM

Docker Compose brings up the server, the engine and the connectors in one command. Terraform modules exist for GCP, AWS and Azure.

Kubernetes

A Helm chart that scales engine workers and validates its own values.

Air-gapped

The whole distribution installs with no network calls at install time or first launch, and nothing phones home at any point. Local embedding models through Ollama or HuggingFace keep the vector features offline too.
# Python 3.12 — 3.13 is not supported.
# Not Linux aarch64: no pgserver wheel, so the embedded tier does not run there.
python3 -m venv .venv && source .venv/bin/activate
pip install "provisa[embedded]"

provisa run          # your data
provisa run --demo   # the bundled sample domains, on embedded SQLite

The embedded tier runs on DuckDB. No JVM means no Trino — multi-engine federation comes from pointing the install at an engine you run.

Provisa is self-hosted. You run it on your hardware, in your cloud account, or air-gapped. There is no managed service to buy today.

The published artifact is 0.1.0a479, pre-1.0. Of 1,872 tracked requirements, 1,599 are complete, and the per-requirement status is in the repository you can read before you talk to us.
