Architecture

One model, one compiler, an engine you can replace.

Provisa sits between the sources you already run and the people and programs that query them. It holds one model — sources, tables, columns, relationships, domains, roles, rules and views — and compiles every incoming request against it. What comes out is a single canonical PostgreSQL-style statement, translated into the dialect of whatever will run it, so the protocol you connected with does not change the SQL.

That is also why one question can be asked once, in English, and answered on up to six governed surfaces — SQL, GraphQL, Cypher, gRPC, JSON:API and OpenAPI — each one generated for the asking role and run through the same compiled governance. Where the six come from. The gRPC, JSON:API and OpenAPI three are the request and the response envelope a client of those protocols would exchange, computed through the pipeline rather than over a socket, and they express row, aggregate and group-by questions; an arbitrary question is carried by SQL, GraphQL and Cypher.

Provisa is at 0.1.0a479, pre-1.0. 1,599 requirements complete and 84 in progress, counted on 14 October 2026. Every capability on this page names the requirements behind it, and their status is in the repository.

01 Routing

Four routes. Provisa picks, you can override.

01
Straight to the source A statement touching one relational source bypasses the federation engine entirely and goes to that database over its own driver, transactionally.
02
Through the engine A statement that joins across sources fans out through the federation engine. Governed identically to the direct route — same compiled statement, same role.
03
Through a replica A source the engine cannot reach in place is read from a copy Provisa maintains in a store the engine reads quickly.
04
Overridden When the default is wrong for a particular table or view, a steward sets the route.
MUTATIONS Mutations to a database always go straight to that database, never through the engine.
02 Compilation

Your request becomes SQL. Then your role rewrites it.

The first stage turns the request — GraphQL, Cypher, REST, a protocol buffer, or SQL — into plain SQL against the semantic model. The second rewrites that SQL under the caller's role, applying row filters, masking and column visibility, whatever shape the SQL takes: subqueries, CTEs, joins, star expansion. Because the second stage needs only SQL and a role, every client path gets the same enforcement.

SELECT c.name, c.email, o.total
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.total > 1000;
# Returns the governed SQL for a question, with row filters and masks
# inlined, plus the route, the parameters and the enforcement metadata.
# Executes nothing. The question goes in as GraphQL.
curl -X POST https://provisa.internal/data/compile \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"query": "{ customers { name email orders(where: {total: {gt: 1000}}) { total } } }"}'

Not the result. A description of what the compiler did, by field name, per role — which is the thing you cannot get from a database:

The enforcement object the compile-only route returns, by field name
Field What it holds
rls_filters_applied The predicate text injected, per table
columns_excluded table.column for every column stripped for this role
masking_applied table.column -> <mask_type> per masked column
schema_scope role:<role_id>
ceiling_applied The row or time ceiling, when one fired
route The routing decision from Routing, above

Alongside it: the compiled semantic SQL, the engine SQL or direct SQL, the parameters, the sources touched, and which optimizations fired — MV rewrite, hot-table inlining, the cache service. The enforcement is enumerable before the query runs.

Semantic SQL is the one dialect throughout. It has no array, struct or map type — nested data comes back as JSON — and because objects are defined in the model rather than by SQL, CREATE, DROP, ALTER and TRUNCATE are refused on every surface.

03 The model

Four things, and nothing is exposed until you say so.

Sources

Name a type, give connection details. Provisa checks the connection before it saves anything, and the source is live without a restart. Connecting a source exposes nothing.

Tables

A table is queryable only after someone registers it. An unregistered table is invisible: absent from the schema browser, unnameable in a query. The published schema is what the business chose to publish, not the raw layout of the database.

Relationships

How tables join. Provisa proposes candidates from foreign keys and ranks them by how much evidence backs each one; a steward confirms or rejects. Cross-source relationships are declared by hand with a cardinality.

Domains

Business areas with a steward each. A domain decides which other domains may read its tables, and anything crossing the boundary is approved by the domain that owns the data.
TWO AT ONCE A relationship is two artifacts at once. It is the governance rule deciding whether a join is legal, and it is the join shape the materialized-view optimizer needs. Approving relationships buys query acceleration as a byproduct.
04 Semantics

Defined once, and deliberately kept apart.

Metrics

A metric is a named, governed aggregate with one definition. Write it once and every query surface uses it in that surface's native syntax. Facts and dimensions compose in Explore, within the domains the caller can reach.

The concept graph

Every column resolves to a term by a deterministic rule, so cust_id, customerId and CUSTOMER_KEY land on one customer with one definition. Terms relate to each other through a fixed vocabulary of ten SKOS-style relation types.
HELD APART The two are held apart on purpose. A metric does not become a concept because someone tagged it, and a concept does not acquire a number because someone wrote a definition.
05 Placement

What is read in place, what gets copied, and who decided.

This is a property of the running system, not a policy we wrote down, and the system will answer it per engine. On a Trino engine, 63 of the 72 source types are reachable and 37 of those are read live with no copy. The three rows below are that split.

What a Trino engine reads live with aggregates pushed down, what it reads live with predicates only, and what Provisa replicates
Placement What is pushed down Source types
Live, in place Predicates and aggregates PostgreSQL · MySQL · MariaDB · TiDB · CockroachDB · YugabyteDB · Greenplum · SingleStore · SQL Server · Oracle · Exasol · Snowflake · Databricks · BigQuery · Redshift · ClickHouse · Iceberg · Delta Lake · Hive · Hive on S3
Live, in place Predicates only. Aggregates run above the source MongoDB · Cassandra · Redis · Elasticsearch · Kafka · Prometheus · Salesforce · ServiceNow · SharePoint · Splunk · cloud inventory
Read and replicated Provisa lands a copy the engine can query OpenAPI and remote GraphQL services · gRPC services · Neo4j · SPARQL · WebSocket · RSS · SQLite · SAP HANA · HiveServer2 · Cosmos DB · Qdrant · Firebird · Airport · Google Workspace · Microsoft 365 · GovData · log files · Node and Python sources · remote Trino · Fabric · Synapse · the two data-quality checkers · the profiler

Druid and Pinot push predicates and aggregates, but not joins.

WHO DECIDED The split follows from what the engine can reach, not from a setting you tune — change the engine and the table changes with it. If a replica cannot be built, the read is refused with a message naming the table and the cause. It is not answered from nothing.

Hot tables

A small lookup table that many queries join against is held in Redis and injected into the statement as an inline set of rows, so the join never leaves memory. A table becomes hot automatically when it is the target of a many-to-one relationship or its row count is under a threshold.
06 Engines

32 engine keys, and a capability gradient between them.

A source type says where data lives. An engine is the runtime Provisa compiles that data's queries into — the thing holding the connectors, executing the plan and owning the materialization store. They are separate registries, which is why Provisa can read a Trino cluster as a source, run on one as an engine, or do both at once against different clusters.

The three engine classes and what changes between them
Class Keys What changes
Federating trino trino-byo pg duckdb clickhouse clickhouse-server Read sources in place through connectors. A cross-source join runs without landing its inputs first
Warehouse snowflake databricks bigquery fabric synapse Partial federators. The warehouse executes what it reaches natively and lands everything else into itself first
SQLAlchemy One generic runtime, pre-named for twenty databases from mysql to teradata, and a sqlalchemy key that takes any URL No federation connectors at all. Everything lands in the target store and is federated with plain SQL
THE GRADIENT Pick a warehouse engine and the claim changes shape. "Swap in Snowflake and nothing copies" is not true — what Snowflake cannot reach natively lands in Snowflake first. The gradient is the honest version and it is the one you can plan against.

Each engine declares what it can do, and the planner reads those declarations when it decides what to push down and what to pull back. 32 engine keys in total: six federating, five warehouse, and one generic SQLAlchemy runtime pre-named for twenty databases.

PG ENGINE Running the pg engine against your own PostgreSQL means installing the extensions it federates through. The bundles are copied into the server's own library directory, so they need filesystem access to the Postgres host — a managed service that does not give you that, such as Amazon RDS or Cloud SQL, cannot take them; use the extensions the service offers instead. The bundles are built for PostgreSQL 16 only, on linux-x64 and darwin-arm64, and anything else is refused by name rather than falling back to a source build. 
pip install provisa-pg-ext
provisa pg-ext install --docker my-postgres
docker restart my-postgres      # pg_duckdb loads only at server start
provisa pg-ext install --docker my-postgres --create
07 Provenance

Traced from the statement, without running it.

From a single SQL statement — through CTEs, subqueries, joins and inline command calls — Provisa builds the column-level lineage, and merges every statement it has seen into one provenance graph across every view and materialized view in the estate. No execution is required to produce it.

The graph

One box per relation with its columns as rows, arriving collapsed when it is large, and read through a role you pick on the form — so you can ask what a particular role's view of provenance looks like, not just the administrator's.

Point in time

A table can record row-level changes into an append-only delta ledger. From the ledger a materialized view is rebuilt as it stood at an earlier moment, so a report reproduces exactly.
08 Explain

EXPLAIN on the SQL that actually ran.

A raw SQL statement explains itself the way a GraphQL query does. The plan shows the semantic sources it scanned and how it was routed, and carries the row and cost estimates the target engine already computed — whichever engine that is. EXPLAIN and EXPLAIN ANALYZE run against the governed statement, after row filters and masking, so what you are reading is what your role actually caused.

EXPLAIN ANALYZE
SELECT c.name, o.total
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE o.total > 1000;
09 Freshness

One place decides whether a copy is stale.

Staleness bounded by an interval, set per table.

A query, a version token, or a marker file a producer writes when new data is ready.

Row by row, through one path: Debezium topics including Avro, MongoDB change streams, Kafka, and WebSocket.

Tables fed by a signal refresh when the signal arrives.

A steward marks a source load-sensitive and restricts refresh to an off-peak window, a cadence or a change probe — for the operational database that cannot absorb heavy reads.

A write to a source table marks affected views stale, and a stale view is not used. Row security applies after the rewrite, so a stored result never widens what a role can see.

The table's detail page states the resulting policy in plain words.

10 Results

A million rows should not need a different API.

Streaming

pgwire, Flight SQL and gRPC receive rows as the engine produces them. Direct reads use a server-side cursor or an Arrow reader. A million-row scan starts returning rows before the scan completes, holding one batch in memory.

Redirect

Past a size threshold Provisa writes the result to object storage and returns a presigned link that expires. Parquet and ORC are written by the engine straight to the store, so the data never passes through Provisa. Files are readable only by the user who asked, and are cleaned up when the link expires.

Formats

JSON keeps the nested shape of the query. NDJSON streams one object per line. Tabular exports come as one flattened table or as normalized tables with their foreign keys, in Parquet or CSV — normalized on the query itself, not by reshaping a serialized response.
11 Deployment

Same product, same config, same governance, laptop to cluster.

Provisa is stateless in front of its control-plane database, so any number of instances run behind a load balancer. Secondaries read their configuration from the shared database and only the primary writes it. One instance can also run several worker processes sharing the same ports, so every protocol uses all the cores on a machine.

Embedded

A single download driven by start, stop, status and open. Natively, with no Docker: DuckDB as the engine, an embedded PostgreSQL control plane, an in-memory cache. No JVM means no Trino — Trino on Docker or an external engine are opt-in choices in the wizard.

Self-hosted

Docker Compose for a team; a Helm chart for Kubernetes that scales engine workers and validates its own values.

Private cloud

Terraform modules for GCP, AWS and Azure provision the stack, stage the artifacts and run it under systemd. The AWS path builds a multi-node cluster behind load balancers.

Air-gapped

No network calls at install time or first launch, and nothing phones home at any point. Local embedding models via Ollama or HuggingFace keep the vector features offline.
WHERE IT RUNS The embedded DuckDB engine is for desktop, edge and development — not for multi-user production. The control plane is a different question and the answer is better: the embedded tier runs embedded PostgreSQL, which is the default from the desktop install up, so database-enforced audit-log immutability holds there too. SQLite is a selectable control-plane store and it does not enforce it.

Provisa is self-hosted. You run it on your hardware, in your cloud account, or air-gapped. There is no managed service to buy today.
