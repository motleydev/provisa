Products: Provisa, Neo4j, Apollo GraphOS, Starburst, Hasura

**Starburst column last verified: 2026-10-13**, against Starburst Enterprise 482-e.3 LTS
(`docs.starburst.io/latest`) and Starburst Galaxy as documented on that date. Galaxy is
continuously released and carries a date rather than a version.

**Neo4j column last verified: 2026-10-14**, against Neo4j 2026.09 (`neo4j.com/docs`, Operations

The Hasura column is **not** dated and has not been re-verified. Do not publish a negative claim
from an undated column. `/vs/hasura` carries its own claim set and is briefed separately; nothing
in this file licenses a Hasura negative.

Dating a column does not date every cell in it. A cell in the Neo4j or Apollo column is verified
only if it carries its own `(Verified 2026-10-14, ...)` stamp naming the documentation it was read
against. Cells in those columns without a stamp were not re-verified on this pass and are still
subject to the undated rule.

Seventeen cells in the Neo4j and Apollo columns were **false as published** on 2026-10-13 — five
Neo4j, twelve Apollo — and a further eight were too broad to defend. All are corrected below. The
two that would have done the most damage: Neo4j 2026.09 documents
property-based access control with predicate conditions on property values, so "no row-level
filtering equivalent to SQL RLS" was wrong; and the GraphOS Router documents entity caching
separated by authorization context with a per-user `private_id` partition, so "not
security-partitioned by role" was wrong. Both were load-bearing for claims we make about
ourselves. See the publishable-row list at the end of this file before writing a hub row.

A negative claim about a competitor is a claim about their documentation on a date, and belongs in
this file written that way — "their documentation for version X describes no Y", not "they have no
Y". A claim in the second form has no verifiable scope and was wrong three times in the Starburst
column before 2026-10-13.

## Which Neo4j and Apollo rows the Compare hub may publish

Decided 2026-10-14, against the reads stamped in the cells above. The form is the one the Starburst
column settled on: a negative is a claim about their documentation on a date, with the product and
version named.

### Publishable — Neo4j

1. **Cypher is theirs and graph analytics is theirs.** GDS 2026.09 documents centrality, community
   detection, similarity, path finding, node embeddings and topological link prediction. This is the
   fit statement, and it should be unhedged: if the buyer needs deep traversal or GDS, Neo4j.
2. **One store, not many source types.** Composite databases query across Neo4j databases, local or
   on remote DBMSs, through a single Cypher query — name that — and every constituent is a Neo4j
   database. `LOAD CSV` reads files, including from S3, but their documentation describes it as
   import that parses a row at a time into `CREATE`/`MERGE`, so the file does not become a queryable
   table. No REST, GraphQL or gRPC service is a governed source.
3. **Access control hides; it does not transform.** 2026.09 documents read and traverse privileges
   on labels, relationship types and properties, with predicate conditions on property values. It
   describes no mechanism for returning a transformed value, so the outcomes are the real value or
   no value. Our masking row is a transformation claim, not an access-control claim.
4. **Their DENY fails open, in their words.** "A `DENY` rule fails open when its criteria cannot be
   evaluated, which means the restriction is not applied." Quote it, attribute it, do not
   characterise it. An architect reads this as the difference between a filter applied around a
   query and a predicate compiled into one.
5. **Vector embeddings must live in the graph.** Cypher 25 vector indexes are supported, not beta,
   cosine and Euclidean, over properties on nodes and relationships. An external vector has to be
   imported first. No declarative generation, no fallback materialization.
6. **Their catalog is per-role for labels, not for property keys.** `db.labels()` and
   `db.relationshipTypes()` are documented as returning results "according to the user's access
   rights"; `db.propertyKeys()` is documented as listing "all property keys in the database" with no
   such caveat. Publish the documentation asymmetry in those words. Do not publish it as a leak —
   we have not tested the behaviour, and the absence of a caveat in a procedure description is not
   proof that the procedure is unfiltered.

### Publishable — Apollo GraphOS

1. **Composing GraphQL services your teams already built is theirs.** Keep the fit statement, and
   update it: connectors mean a REST API no longer needs a subgraph service either.
2. **The transport is the boundary, and it is their sentence.** `@connect` "can only retrieve data
   from HTTP APIs that return JSON data and, optionally, accept a JSON body" (connect v0.4). No
   database, object store, file, stream or gRPC service is a connector target. This is the strongest
   row available against Apollo and it is a quotation, not a judgement.
3. **Authorization is field-and-type, not row.** `@authenticated`, `@requiresScopes` and `@policy`
   are enforced at the router and filter unauthorized fields and types before execution — say so —
   and their documentation describes no row or record predicate and no value transformation.
4. **Schema differentiation is per variant, not per request.** Contracts filter individual fields by
   `@tag` and publish a separate variant with its own router. A new audience is a new variant to
   compose and operate, not a role resolved at request time.
5. **The air-gapped thing is the router, not GraphOS.** Offline licences exist and the claim must
   concede them: Enterprise, on request, contract-term or one year, 28-day grace, re-fetched and
   redistributed every renewal, supergraph schema read from a local file. The registry, composition,
   contracts and observability stay SaaS. For a buyer whose constraint is no vendor service in the
   deploy path, that is the fact.

### Not publishable

1. **A Neo4j catalog-leak claim.** The documented asymmetry in `db.propertyKeys()` is publishable;
   an assertion that property names actually leak to an unauthorized role is not, because nobody has
   run it. If the hub wants the stronger claim, test it first.
2. **Any Neo4j deployment or SaaS negative.** The deployment, SaaS and air-gap cells in the Neo4j
   column were not re-verified on this pass and carry no stamp.
3. **"Not available" anywhere in the Neo4j or Apollo columns.** Both were false for natural language
   query on 2026-10-13. Treat a bare "not available" as a defect, not a claim.
4. **Any surviving "exceeds all" that includes Neo4j or Apollo.** Security-partitioned caching is
   gone as a unique claim — the GraphOS Router separates cache entries by authorization context and
   supports a per-user `private_id`. Natural language query is gone as a unique claim. Check the
   remaining occurrences against these two columns before a hub row inherits one.
5. **Hasura.** Undated, unverified, out of scope here. Its page carries its own claim set.
6. **Denodo.** No column exists. Nothing in this file licenses a `/vs/denodo` row.
